## ADDED Requirements

### Requirement: Knob hover affordance
When the on-screen touch keypad is rendered in the `device` or `device_cables` style, each of the 4 rotary-encoder knob graphics baked into the V5 chassis render SHALL respond to mouse hover with a visible affordance, so the knob reads as an interactive control rather than decorative artwork.

#### Scenario: Pointer enters a knob's hit-area
- **WHEN** the mouse pointer moves over the on-screen area of one of the 4 knob graphics
- **THEN** the canvas cursor changes to a scroll/adjust-style cursor and a highlight ring is drawn around that knob

#### Scenario: Pointer leaves a knob's hit-area
- **WHEN** the mouse pointer moves off the knob graphic it was previously hovering
- **THEN** the cursor reverts to the default and the highlight ring is removed

### Requirement: Knob scroll-to-turn
When the on-screen touch keypad is rendered in the `device` or `device_cables` style, scrolling the mouse wheel while the pointer is over one of the 4 knob graphics SHALL send a `zynpot` CUIA event for that knob's index, equivalent to turning the corresponding real hardware rotary encoder by one detent.

#### Scenario: Scroll up over a knob
- **WHEN** the user scrolls the mouse wheel up (away from themselves) while the pointer is over knob index `i`
- **THEN** a `zynpot {i},1` event is queued on the same CUIA pipeline used by keyboard bindings and hardware encoders, and the screen currently bound to that encoder index reacts exactly as it would to a real encoder turn

#### Scenario: Scroll down over a knob
- **WHEN** the user scrolls the mouse wheel down (toward themselves) while the pointer is over knob index `i`
- **THEN** a `zynpot {i},-1` event is queued the same way

#### Scenario: Scrolling outside any knob's hit-area
- **WHEN** the user scrolls the mouse wheel anywhere on the keypad canvas that is not over one of the 4 knob hit-areas
- **THEN** no `zynpot` event is generated by the knob-scroll handling

### Requirement: Knob click-to-press
When the on-screen touch keypad is rendered in the `device` or `device_cables` style, clicking one of the 4 knob graphics SHALL send the same `zynswitch` press/release CUIA sequence the corresponding real hardware encoder's push-button produces, so whatever function is currently bound to that switch index (short, bold, or long press) fires unchanged.

#### Scenario: Press and quick release on a knob
- **WHEN** the user presses and releases the mouse button over knob index `i` within the short-press timing window
- **THEN** `zynswitch {i},P` is queued on mouse-down and `zynswitch {i},R` is queued on mouse-up, and the currently active screen's short-press handling for switch index `i` runs exactly as it would for a real encoder press

#### Scenario: Press and hold on a knob
- **WHEN** the user presses the mouse button over knob index `i` and holds it past the bold/long-press timing threshold before releasing
- **THEN** the same bold/long-press CUIA classification the existing `zynswitch` timing logic already applies to hardware/keyboard presses applies unchanged, with no separate timing logic in the knob handler

#### Scenario: Visual press feedback
- **WHEN** the mouse button is held down over a knob
- **THEN** a press-outline overlay is shown on that knob, matching the visual feedback already used for the 20 keypad buttons, and is hidden on release

### Requirement: Knob interactivity scoped to device-style keypads
Knob hover, scroll, and click handling SHALL only be active when the keypad style is `device` or `device_cables`, and SHALL correctly account for the `device_cables` style's additional top cable-graphics margin when positioning the 4 knob hit-areas.

#### Scenario: Classic or standard style
- **WHEN** the keypad is rendered in the `classic` or `standard` style (no chassis render, no knob graphic present)
- **THEN** no knob hit-areas, hover/scroll/click bindings, or CUIA events related to knobs are created

#### Scenario: Device style without cable margin
- **WHEN** the keypad is rendered in the `device` style
- **THEN** the 4 knob hit-areas are positioned directly over the knob graphics in the chassis render with no additional vertical offset

#### Scenario: Device_cables style with cable margin
- **WHEN** the keypad is rendered in the `device_cables` style
- **THEN** the 4 knob hit-areas are shifted down by the same cable-margin offset already applied to the chassis render and the 20 button hit-areas, so they remain aligned with the knob graphics
