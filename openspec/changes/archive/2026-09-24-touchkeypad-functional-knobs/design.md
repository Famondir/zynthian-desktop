## Context

`zynthian_gui_touchkeypad_v5` (in the `Famondir/zynthian-ui` fork, branch `vangelis`, cloned by `docker/Dockerfile`) draws the `device`/`device_cables` keypad styles by compositing an invisible, transparent `PhotoImage` hit-area on top of the baked-in V5 chassis render (`icons/v5_mockup/v5_render_zenital_mockup_1910.png`, 1910x960px) for each of the 20 buttons (`draw_button_device()`), then routes clicks through the existing `zynthian_gui_config.zyngui.cuia_queue` as `"zynswitch {i},P"`/`"zynswitch {i},R"` strings - the same CUIA protocol the keyboard bindings (`zynthian_gui_keybinding.py`) and real hardware GPIO callback (`zynthian_main.py`'s `zynpot_cb`, wired to `lib_zyncore.setup_zynpot_cb`) already use. The render's 4-knob rotary-encoder column exists only as pixels; `touchkeypad-visual-styles`' own tasks.md (task 5.14) explicitly deferred making it interactive, noting the user already has an *unrelated* scroll-to-adjust path (mouse wheel over the on-screen value-controller widgets in `zynthian_gui_controller.py`'s `cb_canvas_wheel`) that has nothing to do with the keypad image.

This change fills that gap: turn the 4 knob graphics into real input surfaces feeding the same `zynpot`/`zynswitch` CUIA pipeline, using the same "invisible hit-area over baked pixels" pattern already proven for the 20 buttons - no new dispatch mechanism, no changes outside `zynthian_gui_touchkeypad_v5.py`.

Knob pixel geometry was measured directly against the vendored render (script-driven crop/overlay, not eyeballed) since the only prior reference (tasks.md 5.14: `(1658,125) group offset, r=52`) turned out to be a rough note, not a verified value. The first measurement pass assumed uniform vertical spacing and shipped `V5_KNOB_GROUP=(1711,197)`/`V5_KNOB_SPACING_Y=198`/`V5_KNOB_RADIUS=44` (task 1.1) - task 6.3's visual pass (user-reported: rings too large, upper three knobs' hit-areas sitting too low, bottom knob's sitting too high) found that assumption wrong. A second, edge-detection-based measurement pass against the raw asset (union of non-background pixels per row across a band spanning each knob, to avoid the knob's internal dark "pointer" wedge - which sits at a different rotational angle per knob - being mistaken for background) showed the true per-knob vertical spacing is *not* uniform:

| Knob | Final center (x, y) | Spacing from previous |
|------|------------------------|------------------|
| 1 (top) | (1718, 178) | - |
| 2 | (1718, 378) | 200px |
| 3 | (1718, 586) | 208px |
| 4 (bottom) | (1718, 799) | 213px |

Radius was tightened from 44px to 38px (the original value overshot visibly past the metal rim). These land inside `V5_SCREEN_RECT`'s right margin (screen ends at x=731+800=1531, image is 1910 wide), matching the real panel's knob column sitting to the right of the screen.

## Goals / Non-Goals

**Goals:**
- Make the 4 on-screen knob graphics (in `device`/`device_cables` styles only) respond to mouse hover, scroll wheel, and click, using the same visual-affordance and CUIA-dispatch conventions `draw_button_device()` already established for the 20 buttons.
- Reuse the existing `zynpot`/`zynswitch` CUIA pipeline unchanged - a knob interaction must be indistinguishable, from every downstream screen's point of view, from the same interaction via keyboard binding or real hardware.
- Keep `classic`/`standard` styles (which have no chassis render, hence no knob graphic) completely unaffected.

**Non-Goals:**
- A physically-accurate rotary drag gesture (click-drag-in-a-circle to turn, like some synth-UI knob widgets). Scroll wheel is the interaction the user asked for and the one the codebase already uses elsewhere (`cb_canvas_wheel`, keyboard `Comma`/`Period`) - consistent, not novel.
- Changing what any `zynpot`/`zynswitch` index *does* on any given screen - that logic (`zynpot_cb`, `cuia_v5_zynpot_switch` overrides per screen) is entirely pre-existing and out of scope.
- Re-deriving or correcting `touchkeypad-visual-styles`' button/LED/screen geometry - only new knob-specific constants are added.
- Touch/tap-and-hold rotary gestures for actual touchscreen hardware (this keypad's `device`/`device_cables` styles are a desktop-test-rig concept; scroll wheel assumes a mouse).

## Decisions

- **Same hit-area technique as buttons, new `draw_knob_device()` method.** A fully transparent `ImageTk.PhotoImage` per knob, `create_image`'d at the knob's bounding box and tag-bound to `<Enter>`/`<Leave>`/`<Button-4>`/`<Button-5>`/`<Button-1>`/`<ButtonRelease-1>`, mirroring `draw_button_device()`'s existing `<Button-1>`/`<ButtonRelease-1>` pattern. New constants follow the file's existing `V5_*` naming: `V5_KNOB_CENTER_X = 1718`, `V5_KNOB_ROWS = (178, 378, 586, 799)` (per-knob Y offsets, not a single top+spacing formula - see below), `V5_KNOB_RADIUS = 38` (hit-radius, sized to the visible knob face including its metal rim). Like every other `V5_*` constant in this file, these went through several rounds of visual correction before landing (task 6.3) - the same workflow the button/LED constants went through in `touchkeypad-visual-styles/tasks.md` 5.7-5.13. `V5_KNOB_ROWS` uses an explicit per-knob tuple rather than a single `TOP_Y`/`SPACING_Y` pair (unlike the first draft) because task 6.3's re-measurement found the true vertical spacing between knobs isn't uniform (200px/208px/213px) - the same reasoning `V5_BUTTON_ROWS` above already applies to the 5 button rows.
- **Knob index = visual top-to-bottom order (0=top/"1" ... 3=bottom/"4"), matching the render's own baked-in "1/2/3/4" labels.** This is the same index space `zynpot`/`zynswitch` CUIAs already use (`ZYNPOT 0..3`, `ZYNSWITCH 0..3`), and the render's labels are the only physical reference available without real V5 hardware; if user testing shows the physical wiring order differs, only the constant's ordering needs to change; wiring, exact behavior are unaffected either way.
- **Scroll wheel → `zynpot {i},{+1|-1}`, not an accumulated/scaled delta.** One wheel notch (`<Button-4>`/`<Button-5>`, the standard X11 mouse-wheel binding already used throughout this codebase, e.g. `zynthian_gui_controller.cb_canvas_wheel`) = one encoder detent, matching both the real encoder's per-detent CUIA and the existing keyboard binding (`Comma`/`Period` → `ZYNPOT 3,-1`/`ZYNPOT 3,1`). No custom acceleration curve - whatever the current screen's `zynpot_cb` does with a run of `±1` deltas (some screens already implement their own repeat/acceleration) applies unchanged.
- **Click → `zynswitch {i},P`/`zynswitch {i},R`, exactly like the button hit-areas.** `cb_button_push`/`cb_button_release` already exist and do exactly this (offset by `+4` for the 20 keypad buttons, since indices 0-3 are reserved for the 4 encoder switches); the knob handlers call the *unshifted* index directly into the same `cuia_queue.put_nowait(f"zynswitch {i},P")` pattern, so short/bold/long-press timing (handled entirely in `zynthian_gui.py`'s CUIA thread, `zynswitch_timing()`) works unchanged. No new press-timing logic.
- **Hover changes cursor + shows a pre-created glow ring; the press-outline and the ring both toggle between `state="hidden"` and `state="disabled"` - never `state="normal"`.** Cursor feedback (`self.config(cursor="sb_v_double_arrow")`, scoped to the whole canvas while hovering a knob) signals "this responds to scroll"; a highlight ring (`create_oval`, `zynthian_gui_config.color_hl`) gives a visible focus state without altering the baked-in knob artwork.

  **Revised twice during implementation, both times after reproducing a real livelock during manual testing** (UI fully unresponsive, including to SIGINT/SIGTERM - Tkinter's default callback-exception handling swallows the resulting `KeyboardInterrupt` and keeps the mainloop going, so only `SIGKILL` on the Python process actually closes it):
  1. *First version*: `create_oval()`/`delete()` per `<Enter>`/`<Leave>`, tagged with the same `v5_knob_{index}` tag the hit-area's own bindings use. The newly-created ring becomes the topmost item under the pointer, which fires `<Leave>` on the shared tag (deleting the ring) then `<Enter>` again (recreating it) - an infinite crossing-event loop.
  2. *Second version* (looked right, still broke): pre-create the ring once, hidden, with no tag of its own, and only ever `itemconfig(state="normal"/"hidden")` it afterwards - same for the pre-existing press-outline (`KNOB_PRESS_ID`, toggled on click). This fixed hover-only interaction but the *click* path (`cb_knob_push` revealing the press-outline as `"normal"`) hit the identical class of bug: **any** item transitioning to `state="normal"` becomes eligible to be Tk's "current" (topmost-under-pointer) item regardless of whether it's freshly created or just unhidden - if that changes what's "current" while the pointer is stationary near an edge, Tk re-fires `<Leave>`/`<Enter>` on the hit-area's tag, and if those handlers toggle *another* overlapping item's state the same way, the two items can ping-pong "current" back and forth forever. Confirmed in isolation (a minimal Tk canvas driven by real X11 `XTestFakeMotionEvent` calls, not Tcl's `event_generate` - the latter doesn't reproduce this at all, since it bypasses the same current-item re-picking path real pointer motion takes): sweeping the pointer across a hit-area's edge with an overlapping same-region item toggling to `"normal"` reliably ran away past 500 Enter/Leave pairs in under a second; a single item sharing the hit-area's own tag (the pattern the 20 buttons already use, and still use, unchanged) stayed at a sane 1-2 crossings under the identical stress - so this was never a risk for the existing button code, only for a *second* item newly introduced by the knobs.
  3. *Actual fix*: both the hover ring and the press-outline toggle between `"hidden"` and `"disabled"`, never `"normal"`. Tk's `"disabled"` item state still draws the item (using the regular `fill`/`outline` since no `disabledfill`/`disabledoutline` override is set) but permanently excludes it from "current item" picking - so toggling it can never change what the pointer is "over" for crossing-event purposes, no matter how many times or how close to an edge it happens. Re-verified the same isolated edge-sweep stress with `"disabled"` (2 crossings, stable) and then the equivalent combined edge-dwell/click-hold/rapid-click stress directly against the running app's 4 real knobs - stable, no livelock.
- **`cable_margin` y-offset applies identically to knobs.** `device_cables` reserves a 160px strip above the render for cable graphics; `draw_button_device()` already adds `self.cable_margin` to every button/LED y-coordinate. `draw_knob_device()` does the same for knob y-coordinates, so knob 1's actual canvas y is `self.cable_margin + V5_KNOB_GROUP[1]`, keeping `device` and `device_cables` knob behavior identical modulo that fixed vertical shift.
- **Gate entirely on `self.style in ("device", "device_cables")`**, called from `__init__` right after the existing `draw_fn` button loop, so `classic`/`standard` (no chassis render, no knob graphic to overlay) are untouched - consistent with how every other device-only feature in this file is gated.

## Risks / Trade-offs

- [Measured knob coordinates could still be slightly off on user's actual display] → Mitigated the same way button/LED geometry was: ship a reasonable starting value, iterate from user screenshots (this file already has a track record of exactly that workflow).
- [Knob-index-to-physical-encoder-order assumption (top-to-bottom = 0..3) is inferred from the render's printed labels, not confirmed against real V5 wiring docs] → Low blast radius: wrong only means knob "2" drives what a user expects from knob "3" etc.; trivially fixed by reordering one constant, no functional/protocol change.
- [Adding 4 more bound canvas items increases event-dispatch surface on an already class-heavy canvas] → Consistent with the existing 20-button + LED pattern already in this file; no new architectural concern.
- [Tk's `<Button-4>`/`<Button-5>` scroll binding is X11-specific (not Wayland-native, not Windows/`<MouseWheel>`)] → Matches the project's existing runtime target exactly (`zynthian-desktop-runtime` spec: real `jackd`/X11 desktop stack) and the identical binding already used elsewhere in this same codebase (`cb_canvas_wheel` and others) - not a new constraint this change introduces.
- [Any canvas item overlapping a hit-area, if toggled to `state="normal"` in response to `<Enter>`/`<Leave>`/click, can win Tk's "current item" picking and re-trigger those same crossing events on the item(s) underneath - livelocking the Tk mainloop unresponsive to everything, including SIGINT/SIGTERM] → Hit twice and fixed during this change's own implementation (see the hover-ring decision above, including the isolated real-X11 test that proves it). Noted here explicitly since it's a general Tkinter-canvas gotcha, not specific to knobs, and easy to reintroduce by "obvious-looking" code: any future per-item hover/highlight/press effect on this canvas that overlaps an existing hit-area must toggle between `"hidden"` and `"disabled"`, never `"normal"` - a single item sharing the hit-area's *own* tag (the existing button pattern) is fine either way, but a *second*, differently-tagged (or untagged) overlapping item is not safe as `"normal"`.

## Migration Plan

Additive only - new methods/constants in one file, gated behind existing style flags. No data migration, no config schema change, no impact on `classic`/`standard` styles or any other screen. Rollback is reverting the file; `ZYNTHIAN_GUI_KEYPAD_STYLE` continues to gate the whole feature (set to `standard` or `classic` to opt out entirely).

## Open Questions

- Exact hit-radius and cursor glyph are visual-polish choices best settled by looking at the running app on the target display, same as prior `V5_*` tuning rounds - tracked as an explicit tuning task rather than a blocking decision here.
