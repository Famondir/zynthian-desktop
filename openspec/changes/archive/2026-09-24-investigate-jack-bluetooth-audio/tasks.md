## 1. 3.5mm jack investigation

- [x] 1.1 Confirm the jack-detection kcontrols (`Mic Jack`, `Headphone Jack`, `Speaker Phantom Jack` on `hw:sofhdadsp`) actually change value on insertion/removal - watch with `alsactl monitor` (or repeated `amixer -c sofhdadsp cget ...`) while plugging/unplugging. Confirmed live with a headset: baseline both `off`; on insertion, `Headphone Jack` flipped `off→on` first, `Mic Jack` followed ~0.4s later (sequential contact engagement on a combo TRRS jack); on removal, both flipped back to `off`. Real, reliable signal - not a false lead.
- [x] 1.2 Check whether `pyalsa`/`alsaaudio` (whichever ALSA Python binding `zynautoconnect.py` already uses) exposes a way to subscribe to control-change notifications, or whether it would need polling. `zynautoconnect.py` uses `alsaaudio` (pyalsaaudio), only for `alsaaudio.pcms()` (PCM enumeration) - its high-level `Mixer`/`mixers()` API wraps ALSA's *simple-mixer* tree and doesn't even list jack-detection controls at all (confirmed: `alsaaudio.mixers(device='hw:sofhdadsp')` omits `Mic Jack`/`Headphone Jack`/`Speaker Phantom Jack` entirely - they live in the lower-level `snd_ctl_*` API instead, which pyalsaaudio doesn't wrap). `pyalsa` (the lower-level binding that *would* expose real control-change events) isn't installed and isn't currently a dependency anywhere. Doesn't matter in practice, though: `auto_connect_thread()` (the function driving `update_hw_audio_ports()`/`update_hw_midi_ports()`) is **already a plain polling loop** (`while not exit_flag: ... sleep(deferred_inc)`, checking every ~2s via `deferred_timeout`), not event-driven at all - matches the ~2s bridging time observed in `fix-audio-hotplug-support`'s own testing. So no new event-subscription machinery or dependency is needed either way: a subprocess-based `amixer -c sofhdadsp cget numid=11` (or equivalent) check on the same existing 2s cycle fits the codebase's established pattern directly.
- [x] 1.3 Prototype (throwaway script, not wired into `zynautoconnect` yet): react to a jack-insertion event and confirm it's reliably distinguishable from other control-change noise on this card. Targeted numid reads (`amixer -c sofhdadsp cget numid=11/12`) are inherently unambiguous - no diffing against the full control set, so unrelated changes (e.g. `Master`/`Capture` volume) can't be mistaken for a jack event. One real finding: `numid=13` ("Speaker Phantom Jack") reads a stable `on` at all times regardless of anything being plugged in - a "phantom jack" (this codec has no real sense pin for the built-in speaker output, so it always reports "connected"). Only `Mic Jack`(11)/`Headphone Jack`(12) are real, meaningful signals; 13 should be ignored, not treated as a hotplug trigger.
- [x] 1.4 Decide: worth wiring into `zynautoconnect`'s hotplug path (estimate effort/risk from 1.1-1.3), or document as a permanent limitation. Record the decision and reasoning in design.md's "Decisions" section. **Decision: worth implementing** (low effort, fits the existing polling loop, no new dependency) - but reframed during investigation as jack-presence-aware *capture-port gating* (the onboard mic port already exists permanently at the ALSA/JACK level; jack-sensing only tells you whether it's actually in use), not full `alsa_in`/`alsa_out`-style hotplug bridging like the USB case. See design.md's "Decisions" section for the full writeup. Not implemented here per this change's Non-Goals - needs a follow-up change.

## 2. Bluetooth audio investigation

- [x] 2.1 Confirm directly (not just inferred from `run_zynthian.sh` stopping PipeWire): with a Zynthian session running, is there *any* ALSA/JACK-visible trace of a connected Bluetooth device (check `aplay -l`, `pactl`/`wpctl` if anything's still listening, `jack_lsp`)? Confirmed live with the actual AirPods (paired and actively connected via `bluetoothctl`): even *with PipeWire still running*, the AirPods only ever appear via `wpctl status`'s own `bluez5` module view - never in `aplay -l`'s raw ALSA card list. With PipeWire stopped (same as a real Zynthian session), `aplay -l` shows only the 4 expected cards (onboard `sofhdadsp`, `Loopback`, `SUPREMA`, `AG03MK2`) - zero Bluetooth trace at the ALSA level, confirming Bluetooth audio is a pure PipeWire-userspace construct here, not something that would ever surface to `zynautoconnect`'s ALSA-card-level hotplug scan regardless of PipeWire's running state.
- [x] 2.2 Install `bluealsa` and test standalone (Zynthian session stopped) whether `bluealsa-aplay`/`bluealsa-rec` can move audio for the already-paired AirPods, independent of PipeWire. Confirmed live and audibly: installed `bluez-alsa-utils` (package name on this Ubuntu 24.04 system; ships `bluealsa`/`bluealsa-aplay`, no separate `bluealsa-rec` binary in this version, 4.1.1). With PipeWire stopped and the AirPods reconnected fresh (a PipeWire-held BT connection drops when PipeWire stops - had to reconnect via `bluetoothctl` with bluealsa already running for it to claim the A2DP media endpoint), `bluealsa-aplay -L` listed a real PCM device (`bluealsa:DEV=60:FD:A6:12:14:46,PROFILE=a2dp`, SBC, S16_LE 48kHz stereo), and `speaker-test -D bluealsa:...` produced real, audible sound confirmed by the user with AirPods actually in-ear (first attempt with AirPods not in-ear produced a clean-looking stream but no sound - AirPods Pro's in-ear detection mutes playback when not worn, a real gotcha worth noting for anyone repeating this test). Both channels confirmed audibly in isolation (`speaker-test -s 1`/`-s 2`) - left and right both came through correctly; the default cycling test's "nothing on the right" impression was a timing/sequencing artifact of that mode, not a real channel problem.
- [x] 2.3 If 2.2 works, prototype routing `bluealsa-aplay`'s output into a dedicated `snd-aloop` card the same way `setup_virtual_devices.sh`'s `--with-fluidsynth` mode already does for dev testing - then check whether `zynautoconnect`'s existing bridging picks it up as a normal ALSA capture/playback source. Two real findings:
  1. **The existing `alsa_out` bridge binary (from `jackd2`, what `fix-audio-hotplug-support` already uses for every USB device) crashes outright on a `bluealsa:DEV=...,PROFILE=...` device string** - reproducible `*** buffer overflow detected ***: terminated` immediately on startup, confirmed not an environment issue (same binary works fine with a plain `hw:Loopback,0` string). Root cause not dug into further (would need `jackd2` upstream source), but this rules out pointing `alsa_out`/`alsa_in` directly at a bluealsa PCM string as a viable approach - it's not just untested, it actively doesn't work.
  2. **Routing through `snd-aloop` as an intermediary does work, confirmed audibly end-to-end.** Set up a plain `arecord -D hw:Loopback,1,0 | aplay -D bluealsa:DEV=...,PROFILE=a2dp` pipe (no `alsa_out`/`alsa_in` needed for this leg - plain ALSA tools bridge cleanly), then played a tone into the Loopback's *other* side (`hw:Loopback,0,0`) with `speaker-test` - user confirmed hearing it through the AirPods. `zynautoconnect` already treats `Loopback` as a normal ALSA device via its existing hotplug polling (confirmed earlier this session, both in `fix-audio-hotplug-support` and `support-virtual-test-devices` testing) - no changes needed there for the ALSA-level discovery half.

  Net: a viable path exists - keep a persistent `snd-aloop` card, run a small always-on `arecord`/`aplay` (or `bluealsa-aplay`/`bluealsa-rec`) bridge process piping Loopback↔bluealsa (started/stopped based on BlueZ connection state), and `zynautoconnect`'s existing Loopback-card handling does the rest automatically. Note: had to stop PipeWire and reconnect the AirPods for bluealsa to hold the A2DP transport at all - PipeWire and bluealsa both try to claim the same BlueZ media endpoint, consistent with task 2.1/design.md's framing (this only works during an actual Zynthian session, when PipeWire is already stopped for other reasons).
- [x] 2.4 Assess latency/quality of the bridged path - Bluetooth audio (A2DP especially) has inherent latency that may be unacceptable for live playing, independent of whether the bridge technically works. Real numbers captured from the 2.3 test session: BlueZ itself reported an AVDTP transport `Delay: 0x05dc (1500)` on connect - per BlueZ's `MediaTransport1.Delay` property (units of 1/10ms), that's **150ms** of inherent A2DP/SBC codec+radio delay, before any of this project's own bridging adds anything. On top of that, `bluealsa-pcm`'s own log showed a "Selected HW buffer: 4 periods x 24000 bytes == 96000 bytes" on the `aplay` leg alone - 24000 frames at 48kHz = **500ms** of additional worst-case ALSA-side buffering (untuned defaults; `arecord`'s capture-side leg adds a similarly-sized, unmeasured amount on top of that). This ad hoc bridge's *total* one-way latency is therefore very roughly 650ms-1s+ - and even a carefully-tuned purpose-built bridge (small periods, minimal buffering) couldn't get below the ~150ms AVDTP floor, since that part is inherent to A2DP/SBC itself, not this project's plumbing. For reference, comfortable real-time playing feel generally needs well under ~20-30ms round-trip - 150ms alone is already deep into clearly-perceptible, disruptive-lag territory for monitoring your own playing live.
- [x] 2.5 Decide: worth implementing the `bluealsa` bridge (estimate effort/risk and note the latency finding from 2.4), or document as a permanent limitation. Record the decision and reasoning in design.md's "Decisions" section. **Decision: document as a permanent limitation for live/real-time musical use** - not worth implementing for that purpose. The ~150ms AVDTP transport delay alone (2.4) is a hard protocol floor, not an engineering problem this project's bridging could tune away, and it's well past the threshold where a live-monitoring round trip feels disruptive. Effort to build the bridge itself is actually low (2.3 proved plain `arecord`/`aplay` piping works, no new upstream patch needed unlike the jack investigation) - the blocker is fundamentally latency, not feasibility. See design.md's "Decisions" section for the full writeup.
  - **Follow-up tuning test** (requested after the initial decision, to double-check the latency number wasn't just an artifact of an untuned prototype): re-ran the bridge with explicit small buffers (`-F 20000 -B 40000`, 40ms instead of the untuned ~500ms default) - confirmed via `bluealsa-pcm`'s log ("Selected HW buffer: 2 periods x 3840 bytes == 7680 bytes") and a 4-tone sequence (`sox`-generated 440/660/880/550Hz) played cleanly through it - user confirmed all 4 tones heard distinctly, no crackling during playback, only a minor click at the very end of the last tone (normal abrupt-stop artifact, no xruns logged). This confirms the ~500ms figure from the first test was avoidable bridge overhead, not inherent - but the ~150ms AVDTP floor remains regardless of tuning, so the decision stands: still a permanent limitation for live playing, just a slightly less bad one (~150-190ms achievable vs. ~650ms-1s+ untuned).
