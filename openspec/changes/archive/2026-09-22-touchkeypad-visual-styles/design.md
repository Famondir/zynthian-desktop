## Context

The keypad canvas sits *behind* the main content frame (`root_frame`), which is lifted above it and placed at an offset (`main_x`/`main_y`) sized to leave room for the keypad. Both the keypad's own geometry and `zynthian_gui_config`'s placement of `root_frame` need to agree on exactly how much space the keypad reserves, or the two draw on top of each other.

## Goals / Non-Goals

**Goals:**
- Keep `classic` behaviourally and visually identical to the pre-existing upstream layout, as a fallback/comparison baseline.
- Make `standard`'s button grid match the real V5 panel's actual 4x5 arrangement.
- Make style selection a pure startup-time choice (env var/script argument), not a code fork.

**Non-Goals:**
- Interactive on-screen encoder widgets - the user already drives encoder-equivalent actions via mouse-hover + scroll wheel; `device`/`device_cables`'s knob-adjacent area is decorative, not a functional control.

## Decisions

- **Single source of truth for geometry.** `zynthian_gui_touchkeypad_v5` exposes `panel_width`/`top_margin`/`button_height` as instance attributes; `zynthian_gui_config.set_touch_keypad()` reads them from the instantiated keypad object instead of recomputing the same formulas independently. This directly fixes a regression where the two drifted out of sync (`panel_width` was left at the old 2-column value after the grid widened to 4 columns), which made the "Add Chain" dialog overlap keypad columns 3-4.
- **Grow the window, don't shrink the screen, for wider-panel styles.** `standard`/`device`/`device_cables` reserve twice the button-panel width `classic` does (4 button-widths vs 2), carved out of the same total `DISPLAY_WIDTH`. Left uncompensated, the app's actual screen area shrinks substantially (e.g. 1280px -> 960px at the 1600px baseline), which squeezes existing dialogs until icon+text buttons overlap. `run_zynthian.sh` instead widens `DISPLAY_WIDTH` for these styles so the screen area stays the same physical size it is under `classic`.
- **Lazy-import `zynautoconnect` in `device_cables`.** The keypad object is built from inside `zynthian_gui_config`'s own module-level init, before `zyncoder.zyncore.lib_zyncore_init()` has run. `zynautoconnect.py` does `from zyncoder.zyncore import lib_zyncore` at its own import time, which copies the then-current value (`None`) and never sees the later reassignment. Importing `zynautoconnect` eagerly at the top of the keypad module made *every* style crash on startup (`AttributeError: 'NoneType' object has no attribute 'zmip_get_flag_active_chain'`), not just `device_cables`. Fixed by importing it lazily inside `draw_connections()` and deferring the first call via `Canvas.after()`, so it only runs once the Tk mainloop (and therefore `lib_zyncore_init()`) has already completed.
- **Keep `classic` byte-for-byte behaviourally identical**, including its original `"CTRL/PRSET"` label typo, as an explicit fallback style rather than only living in git history.
- **Use the official V5 mockup render instead of a flat vector recreation for `device`/`device_cables`.** Initially built as a flat vector chassis (no licensing question, scales cleanly to any resolution) - superseded once `zynthian-webconf`'s bundled mockup player assets were found (`mockup/v5_render_zenital_mockup_1910.png`, GPL-licensed, part of the official Zynthian project, used for the same purpose: compositing live UI content onto a device render for demo/tutorial recordings). Its `index.html` also gives exact reference coordinates in a 1920x1000 viewBox: screen at (731, 254, 800x480 - matching the real screen's native resolution exactly), button grid at (68, 155)/(79,154) offset with a 4x5 grid (~122px column spacing, ~113px row spacing), knob column at (1658, 125) with ~200px vertical spacing between the 4 knobs.
- **Draw LED backlight rectangles *behind* the chassis image, not on top.** Verified against the PNG's actual alpha channel that most button label/glyph areas (BACK/NO's text, arrow glyphs, the panic "!" icon's plate, the device's outer silhouette margin) are transparent or semi-transparent cutouts meant to let a page background/backlight colour show through - matching the real mockup's own SVG order (`<svg id="leds">` and the render's silhouette drawn before/behind `<image id="v5_render">`, page background white). This means: (a) a white rectangle has to sit directly behind the whole render (not just changing the canvas's default bg, since device_cables' own cable-graphics strip above the render should stay dark), and (b) each button's backlight colour has to be drawn *before* the render image (`draw_button_led()`), with the actual clickable hit-area/press-outline drawn *after* it on top (`draw_button_hitarea()`) - two passes over all 20 buttons instead of one. The backlight shape is a rectangle covering the whole button footprint, not a small circle at the nominal LED coordinate, since a circle doesn't reliably cover wider cutouts like the full word "BACK".
- **`set_button_color`'s dedup must key on the literal colour for device styles, not "mode".** `zynthian_wsleds_v5.py` sets many buttons (BACK, all 4 arrows) unconditionally to a fixed colour (`wscolor_red`/`wscolor_yellow`) on every refresh - colours that don't match any of the 4 named modes (`default`/`alt`/`active`/`active2`) the touch-keypad's colour-to-mode translation layer recognizes, so `mode` comes through as `None` for them. The per-button `LED_STATE` also starts at `None`, so the existing dedup guard (`if config[LED_STATE] == mode: return`, there to avoid expensive/blinky redraws) saw `None == None` on the very first call and skipped it forever - the colour was never applied, not even once. This only ever happened to work for buttons whose steady colour happens to equal one of the 4 named colours by coincidence (e.g. SEL/YES's green happens to equal `wscolor_active`'s default value). Fixed by handling the device-style branch before that dedup check and keying it on the actual `color` argument instead, since the mode-driven ALT-label logic the guard was written for doesn't apply to a plain rectangle fill anyway.

- **Cable positions are measured off the actual render pixels, not eyeballed - and corrected by direct user measurement where automated detection was off.** The top port-icon row's x-positions aren't in `index.html` (the mockup player has no interactive elements there, only the render itself), so they were found by scanning a horizontal band for bright/opaque pixel clusters (the white line-art against the dark chassis) and grouping nearby clusters into physical port groups. The first automated pass was inaccurate; the user corrected the values directly in the source file and added anchors for ports not yet covered (MIDI-thru/out, LAN, USB-3/2/B). Those corrected values turned out to be measured against a differently-sized reference screenshot (2383px wide vs the render's actual 1910px), so they're scaled by `V5_IMAGE_SIZE[0]/_V5_PORT_REF_WIDTH` at load time (`_v5_port_x()`) rather than hand-converted - re-measuring later just means updating `_V5_PORT_REF_WIDTH` to whatever image was used.
- **Only show a cable when there's an honest "is this connected" signal - never a fake always-on cable - except LAN, which is intentionally static.** Audio/MIDI use real JACK port state (`zynautoconnect`). LAN was first wired to `psutil` network-interface state, but per user clarification the simulation doesn't need to mirror *this development machine's* actual network setup (which might have both WiFi and a wired adapter active - irrelevant noise for what the port represents); it's now always a single static cable. MIDI-THRU and the USB ports have anchors reserved but are deliberately left unwired: unlike JACK ports, there's no available signal from here for "is a real device plugged into this specific USB port", and a cable that doesn't reflect reality would undermine the whole point of `device_cables` for those specifically.
- **At most one cable per physical jack - multiple logical devices sharing it become a numbered list, not extra cables.** Real hardware has exactly `len(anchors)` physical jacks per category (e.g. one MIDI-in DIN jack), but this machine can have more logical devices registered than that (observed: 3 MIDI-in, 2 MIDI-out). Drawing one fanned-out cable per device doesn't match the real device and clutters the strip. Instead, devices beyond the anchor count share the nearest jack's single cable, rendered as a left-aligned, numbered stack of colour-chip labels (`"1. name"`, `"2. name"`, ...) - one row per device, small gaps between rows.

## Risks / Trade-offs

- Four styles to keep working means four times the surface area for layout regressions; mitigated by keeping style-specific branching localized to a handful of clearly-marked spots (`self.style == ...`) rather than duplicating the whole file per style.
- Widening `DISPLAY_WIDTH` for non-classic styles means those styles need a physically wider window/monitor than `classic` at the same screen-content size.
