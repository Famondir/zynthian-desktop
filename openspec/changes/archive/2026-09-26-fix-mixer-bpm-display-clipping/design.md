## Context

The mixer screen's topbar draws two status texts on `zynthian_gui_base`'s `status_canvas`: the tempo (`"120.0 bpm"`) and time signature (`"1 | 4/4"`), both anchored `NE` (top-right) at an x-offset computed as `status_l - status_fs * <multiplier>` (`zynthian_gui_mixer.py:1207-1221`). Because the anchor is top-right, the text grows *leftward* from that point; a `tkinter.Canvas` clips any drawing that falls outside its own pixel width, so if the text is wider than the room between the anchor and the canvas's left edge (x=0), the left portion of the string silently disappears - which matches the screenshot (`)bpm` surviving, the number and `bpm`'s leading letters gone).

Two independently-computed quantities decide whether that fits:

- **Available room** = `status_l` (`zynthian_gui_base.py:114`: `int(self.topbar_width * 0.27)`), where `topbar_width = zynthian_gui_config.screen_width`.
- **Text pixel width** scales with `status_fs` (`0.36 * status_h`, `status_h = topbar_height`), which itself derives from `topbar_fs`/`font_size` in `zynthian_gui_config.py:886-896`: `font_size = ZYNTHIAN_UI_FONT_SIZE or display_width / 40`.

On real V5 hardware, `display_width == screen_width == 800` (the physical LCD *is* the screen; there is no extra chrome), so both quantities scale off the same number and the hand-tuned multipliers (`3.5`, `8.5`) hold.

The desktop/simulated port changes this: `zynthian_gui_touchkeypad_v5.py:80` (`V5_SCREEN_RECT`) pins the mocked screen's content area to a fixed `screen_width = 800, screen_height = 480`, but renders an *additional* button-panel mockup beside/around it, so the outer window/display (`zynthian_gui_config.display_width/display_height`) is sized to fit both panel and screen. The font used to draw the BPM text is inflated relative to the pixel budget reserved for it, so the text overflows past x=0 and gets clipped.

**Confirmed live** (task 1, against the already-running simulator - a `run_zynthian_vnc.sh device_cables` process was found live in this environment, `zynthian_main.py` PID 704713, up for the same style as the reported screenshot): its actual environment is `DISPLAY_WIDTH=1910`, `DISPLAY_HEIGHT=1200`, `ZYNTHIAN_GUI_KEYPAD_STYLE=device_cables`. Working through `zynthian_gui_config.py`'s init order with those numbers pinpoints the exact mechanism, which is narrower than originally hypothesized:

- `topbar_height` (`zynthian_gui_config.py:892`, `screen_height // 12`) is computed **before** `set_touch_keypad()` runs (called later, at `zynthian_gui_config.py:932`). At the point `topbar_height` is computed, `screen_height` still equals the *outer* `display_height` (1200), not the mocked screen's fixed 480. So `topbar_height = 1200 // 12 = 100px` - it is never recomputed after `set_touch_keypad()` later overwrites `screen_width`/`screen_height` to the fixed V5 mock rect (800x480, which would give `480 // 12 = 40px`).
- `status_fs` (`zynthian_gui_base.py:117`, `0.36 * status_h` where `status_h = topbar_height`) inherits that oversized `100px` topbar height, giving `status_fs = 36px` instead of the `14px` a 480-tall mock screen should get - a **2.5x oversized font**.
- `status_l` (`zynthian_gui_base.py:114`, `topbar_width * 0.27` where `topbar_width = screen_width`), by contrast, *is* computed after `set_touch_keypad()` has already fixed `screen_width` to 800 (it runs at `zynthian_gui_base.__init__` time, well after `zynthian_gui_config` module init completes) - so `status_l = 800 * 0.27 = 216px` is correct for the mocked screen.
- Net effect: the reserved room for the tempo text (`status_l - status_fs*3.5`) is computed from `status_fs` (`0.36 * status_h`), but the text itself is drawn at a *different* fraction, `0.25 * status_h` (`zynthian_gui_mixer.py:1212`) - two independent constants that happen to both scale with the same oversized `status_h`. At buggy `status_h=100`: budget `= 216 - 36*3.5 = 90px`, text font size `= int(0.25*100) = 25`. At corrected `status_h=40`: budget `= 216 - 14*3.5 = 167px`, text font size `= int(0.25*40) = 10`. Measured directly against the live X display with `tkFont.Font(family="forkawesome", size=<font size>).measure("120.0 bpm")`: at font size 25 (buggy) the string measures **167px** against a **90px** budget - 77px falls left of x=0 and is clipped by the canvas, consistent with the screenshot's `)bpm` fragment. At font size 10 (correct) it measures **69px** against a **167px** budget - a comfortable fit with wide margin.
  Applying the fix and re-launching the simulator (`device_cables`, same `1910x1200` outer display) confirmed this visually: the topbar now renders `1 | 4/4120.0 bpm` in full, no character clipped. (The two strings running together with no gap between `4/4` and `120.0` is a separate, pre-existing cosmetic quirk of the two independently-positioned canvas items, not part of the clipping bug - task 3's self-measuring offset happens to fix this too, as a side effect of making the two items' positions depend on each other's actual measured width.)
- `forkawesome` **is** installed as a system font here (`fc-list` finds `forkawesome-webfont.ttf`), so a missing-glyph font-fallback is ruled out as a contributing factor - this is purely the `topbar_height`/`screen_height` computation-order bug above.
- Under `classic`/`standard` styles, `screen_height` is derived *proportionally* from `display_height` (`zynthian_gui_touchkeypad_v5.py:798/806`, e.g. `5 * display_height // 6`) rather than pinned to an unrelated constant, so the same pre-adjustment-vs-post-adjustment gap exists but is much smaller in practice (e.g. ~1000 vs. 1200, ~20% off, vs. device/device_cables' 480 vs. 1200, ~150% off) - consistent with this bug being reported specifically against the `device_cables` mockup and not against other styles.

So the actual, confirmed fix target is narrower than "font_size keys off display_width": it is specifically that `zynthian_gui_config.py` computes `topbar_height` (and `font_size`, which has the same `display_width`-before-adjustment issue for other UI elements, though less visibly) from the pre-`set_touch_keypad()` display dimensions, and never recomputes them once `set_touch_keypad()` establishes the final `screen_width`/`screen_height` for the active style.

## Goals / Non-Goals

**Goals:**
- Root-cause why the topbar BPM/time-signature text clips in the simulated/desktop environment.
- Make the fix general: the topbar status text must fit under any current or future keypad style/resolution combination, not just patch the one reported case.
- Preserve the existing look/sizing on real hardware (`display_width == screen_width`) exactly - zero visual regression there.

**Non-Goals:**
- Redesigning the topbar layout or status-icon set.
- Changing tempo/time-signature semantics, zynseq behavior, or any non-visual behavior.
- Touching this repo's own code (`docker/`, `workflow_testing/`) beyond adding a regression check; the runtime fix lives in the `zynthian-ui` fork per this repo's `CLAUDE.md`.

## Decisions

- **Decision: move only `topbar_height`'s (and its dependents `topbar_fs`/`font_listbox`/`font_topbar`) computation to after `set_touch_keypad()` - leave `font_size` itself alone.**
  First attempt moved `font_size` itself too (and switched its basis to `screen_width`), which broke `zynthian_gui_touchkeypad_v5.py:787`'s button-label sizing - that code legitimately reads `zynthian_gui_config.font_size` *during* the touch keypad's own construction (`zynthian_gui_config.py:914`, `touch_keypad = zynthian_gui_touchkeypad_v5()`), which necessarily happens *before* `set_touch_keypad()` corrects `screen_width`/`screen_height` - and it legitimately wants a display-relative font (the button panel's own labels scale with the outer display, per that file's `button_width`/`button_height` calculations at lines 184-199, not with the app's screen content area). Confirmed live: moving/rebasing `font_size` produced `ERROR:zynthian_gui_config.<module>: Can't start touch keypad => partially initialized module 'zyngui.zynthian_gui_config' has no attribute 'font_size'` and a blank app window under the `standard` style. The corrected, minimal fix: `font_size` keeps its original position and `display_width` basis (unchanged - it never caused the reported bug); only `topbar_height` (and the `topbar_fs`/`font_listbox`/`font_topbar` block that already depended on both `font_size` and `topbar_height`) moves to after `set_touch_keypad()`, so it alone picks up the corrected `screen_height`/`screen_width`. This is the narrowest fix that still corrects `status_fs` (which depends only on `topbar_height`, not on `font_size`) without disturbing the touch keypad's own font handling.
  Alternative considered: keep the original computation order but widen `status_l`'s multiplier for non-hardware styles - rejected because it hard-codes a per-style fudge factor instead of fixing the actual ordering bug, and would need re-tuning every time a new keypad style changes the panel/display relationship.
- **Decision: make the status text's reserved width self-consistent instead of a hand-tuned constant.**
  Rather than picking new magic multipliers (`3.5`, `8.5`) that happen to fit today's string lengths at today's font, size the reserved offset from the actual rendered text width (e.g. via `tkFont.Font(...).measure(text)` at draw time) so it can never exceed the canvas regardless of font/DPI/style changes going forward. Alternative considered: just retune the constants for the simulator's current numbers - rejected as it would silently break again the next time `display_width` changes (new keypad style, different VNC resolution, different `ZYNTHIAN_UI_FONT_SIZE`).
- **Decision: add a `workflow_testing` regression check that reads the app's own real Tk font measurement from its log, rather than screenshotting pixels or reimplementing the geometry formula.**
  Originally planned as a screenshot-based pixel check, but on reflection a purely pixel-based check can't actually distinguish "clipped" from "not clipped" without OCR: a clipped render doesn't leave blank space, it fills the same budget with *different* (truncated) glyphs, and a generic pixel-presence/span heuristic can't tell those apart. A geometry-only unit test that reimplements the formula independently was also rejected (as originally noted) - it could pass while the real Tk canvas still clips due to font metrics/DPI it doesn't model, and could silently drift from the real implementation over time.
  The implemented approach: `zynthian_gui_mixer.py`'s `layout_status_tempo()` (added for task 3) already computes the real Tk-measured `timesig_left_edge` on every layout pass - the exact quantity that must stay `>= 0` to avoid clipping. It now logs that value (`logging.info("layout_status_tempo: status_l=%d timesig_left_edge=%d fits=%s", ...)`). `workflow_testing/check_topbar_status_fit.py` launches a native session (via `native_adapter.launch()`, extended with a new `extra_env` parameter to reproduce `device_cables`'s worst-case 1910x1200-outer/800x480-mocked-screen mismatch) and asserts every such log line has `fits=True`. This reuses the existing log-reading test infrastructure (`log_diff.py`'s pattern) instead of adding a new screenshot/pixel-diffing subsystem, and reads ground truth from the app's own real font measurement rather than a parallel reimplementation.
  Found live while wiring this up: `native_adapter.launch()`'s `extra_env` had to be re-exported *after* `source`ing `zynthian_envars_custom.sh` inside the launch script, not just passed via the outer subprocess `env=` - that script unconditionally exports `DISPLAY_WIDTH`/`DISPLAY_HEIGHT`/`ZYNTHIAN_TOUCH_SHOWN` (this machine's real hardware tuning), which otherwise silently overrode the intended test values.
  Verified both directions live: with the `zynthian_gui_config.py` fix temporarily reverted (`git stash`), the check fails with `timesig_left_edge=-79`; restored, it passes.

## Risks / Trade-offs

- [Risk] Reordering `topbar_height`/`font_size` computation to run after `set_touch_keypad()` could affect other UI elements sized off `font_size`/`topbar_fs` (listboxes, buttons, other topbar labels), not just the BPM text → Mitigation: since real hardware's `display_width == screen_width` (`set_touch_keypad()` is a no-op there, or not entered at all), this change is a no-op on real hardware; verify visually in the simulator under every keypad style that other font-sized elements still look correct after the change.
- [Risk] Measuring text width at draw time (via `tkFont`) adds a small per-refresh cost to a status readout that updates on every tempo change → Mitigation: tempo/time-signature text changes are low-frequency (user-driven or song-position driven), not per-frame, so this is negligible.

## Migration Plan

- No data migration. This is a display-only fix in the `zynthian-ui` fork (`vangelis` branch). Steps: fix in `/zynthian/zynthian-ui`, commit, push to `Famondir/zynthian-ui` (required for the Docker image to pick it up - see this repo's `CLAUDE.md` on unpushed fork commits), then rebuild/relaunch the Docker or native simulator to confirm visually.
- Rollback: revert the fork commit(s); no persisted state is touched.
