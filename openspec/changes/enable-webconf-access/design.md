## Context

`zynthian-webconf` (repo `zynthian/zynthian-webconf`) is the browser-based config UI real Zynthian hardware ships alongside `zynthian-ui`. On real hardware it's a separate `systemd` service (`zynthian-webconf.service`, see `/zynthian/zynthian-sys/etc/systemd/zynthian-webconf.service`), started independently of the main UI, advertised over Avahi on port 80 (`/zynthian/zynthian-sys/etc/avahi/services/zynthian-webconf.service`). It's a Tornado-based Python app (its setup pulls `tornado`, `tornadostreamform`, `websocket-client`, `tornado_xstatic`, `terminado`, `xstatic`, `XStatic_term.js` - see `zynthian-sys/scripts/setup_system_debian_amd64_bookworm.sh`), started via `$ZYNTHIAN_DIR/zynthian-webconf/zynthian_webconf.sh`.

Neither this project's native `/zynthian` install nor `docker/Dockerfile`'s image currently clones or runs it - there's no `systemd` in the Docker container and no equivalent launcher for the native desktop port, so today it simply doesn't exist in either environment.

## Goals / Non-Goals

**Goals:**
- `zynthian-webconf` reachable from a host browser when running the app natively via `run_zynthian_vnc.sh`.
- `zynthian-webconf` reachable from a host browser when running the Docker image via `run_zynthian_docker.sh`, without requiring the container to run as root.
- Provisioning (clone + deps) handled the same way `zynthian-ui`/`zyncoder`/etc. already are: at Docker build time for the image, and idempotently at first-run for the native install (matching how `entrypoint.sh` idempotently scaffolds `zynthian-my-data` on every start rather than baking runtime state into the image).

**Non-Goals:**
- No `systemd` unit, Avahi advertisement, or other real-hardware service-management machinery - this is a desktop dev environment, not an appliance image.
- No changes to `zynthian-ui` or `zynthian-webconf` application code itself.
- No auth/TLS hardening for webconf's HTTP endpoint - same trust model as the existing noVNC setup (`NOVNC_BIND=localhost` by default), not a hardened multi-user deployment.

## Decisions

**Run webconf as an independent process, not threaded into the main UI's foreground exec.**
Real hardware runs webconf and the UI as two independent `systemd` services; this design mirrors that instead of coupling their lifecycles.
- *Docker*: `entrypoint.sh` already backgrounds jackd and a2jmidid before `exec`-ing into `zynthian_main.py` as the final foreground process. Webconf joins that same pattern - started in the background, added to the existing `cleanup` trap (`kill -9 "$A2J_PID" "$JACKD_PID"` grows a third PID). This keeps `docker run` a single container/process group, consistent with how the image already runs today, rather than needing `docker-compose` or a second container.
- *Native*: a new standalone script, `run_zynthian_webconf.sh` (sibling to `run_zynthian_vnc.sh`, not folded into it), clones/provisions and starts webconf on its own. It does **not** call `/zynthian/run_zynthian.sh` and is not called by `run_zynthian_vnc.sh` - the two are run side by side in separate terminals when both are wanted, same as a real device's two independent services. This avoids modifying `/zynthian/run_zynthian.sh`, which `CLAUDE.md` says is host-local and not version-controlled from this repo.

**Provision `zynthian-webconf` the same way as `zynthian-ui`: fresh clone at Docker build time; idempotent clone-if-missing for the native install.**
Consistent with how the Dockerfile already clones `zyncoder`/`zynthian-sys`/`zynthian-data` fresh per build (with `CACHEBUST` for the actively-developed branch), and how `entrypoint.sh` idempotently re-scaffolds directories on every container start. `run_zynthian_webconf.sh` does the native-side equivalent: `git clone` into `/zynthian/zynthian-webconf` only if that directory doesn't already exist, then `pip install` its deps into the existing `/zynthian/venv` (which already has `--system-site-packages`, so no new venv is needed).
- *Alternative considered*: vendor webconf into the Docker image build only, leave native unprovisioned. Rejected - the user explicitly wants it usable both locally and from the Docker image.

**Grant `NET_BIND_SERVICE` instead of running webconf on a high port or running the container as root.**
The container already runs as `--user "$(id -u):$(id -g)"` (a deliberate choice - see `run_zynthian_docker.sh`'s Xauthority/bind-mount reasoning) and already adds one capability (`SYS_NICE`, for jackd's realtime priority) rather than running privileged. Real hardware serves webconf on port 80; keeping that same port here (via `--cap-add=NET_BIND_SERVICE` on `docker run`) means the URL/bookmarks/docs stay consistent with real-hardware webconf instead of introducing a Docker-only port number to remember. `-p 8080:80` (host port configurable, container-internal port fixed at 80) publishes it to the host; default host port picked to avoid clashing with anything else already running on 80.
- *Alternative considered*: reconfigure webconf itself to listen on a high port (e.g. 3000) to sidestep the capability grant entirely. Rejected for now - adds a config surface inside webconf we'd need to confirm actually exists (not verified against the actual `zynthian-webconf` source, since it isn't cloned anywhere in this project yet), versus a one-line `--cap-add` that's already precedented by `SYS_NICE`. If task work reveals webconf's port isn't configurable at all and 80 can't be bound even with the capability for some reason, fall back to this alternative.

**Native webconf binds to `0.0.0.0`/all interfaces by default (webconf's own default, unverified until cloned), matching the Docker container's exposed-port model, not restricted to loopback like noVNC's `NOVNC_BIND=localhost` default.**
noVNC defaults to loopback because it's a full remote-control surface for the touchscreen; webconf is a config panel real hardware exposes on the LAN by design (that's what the Avahi broadcast is for), so keeping it reachable from other devices on the network by default matches that existing product expectation. Document this clearly in the new script's header comment, same as `run_zynthian_docker.sh` documents its `xhost +local:docker` implications.

## Risks / Trade-offs

- [Webconf's actual port/config knobs are unverified - `zynthian-webconf` isn't cloned anywhere in this project yet, so the design above assumes port 80 and a `zynthian_webconf.sh` entry point based on the `systemd`/Avahi units and setup script references found in `zynthian-sys`.] → First implementation task clones the repo and confirms `zynthian_webconf.sh`'s actual behavior/port before wiring up the rest; design decisions above (especially the port/capability one) get revisited if reality differs.
- [Exposing webconf on the LAN by default (not loopback-only) is a new network-facing surface on the user's machine.] → Called out explicitly in proposal.md's Impact section and in the new script's own header comment, same treatment `run_zynthian_docker.sh` gives `xhost`.
- [Two more background processes (webconf, plus its dependency footprint) added to both entrypoint.sh and a new native script increases the surface that can fail silently on startup.] → Log webconf's stdout/stderr to a file the same way jackd/a2jmidid already do (`/tmp/zynthian_jackd.log` pattern), so failures are diagnosable rather than swallowed.

## Migration Plan

No data migration - this is new, additive provisioning. Rollout is just building the updated Docker image and running the new native script; nothing to roll back beyond not using the new script/rebuilding without the webconf layers.

## Open Questions (resolved by task 1's research)

- **Port**: confirmed configurable - `zynthian_webconf.py` calls `app.listen(os.environ.get('ZYNTHIAN_WEBCONF_PORT', 80), ...)`, so `ZYNTHIAN_WEBCONF_PORT` overrides the port 80 default cleanly, no code changes needed.
- **HTTPS on 443 is unconditional, not optional**: the same `amain()` also unconditionally does `app.listen(443, ssl_options={"certfile": "cert/cert.pem", "keyfile": "cert/key.pem"})` (paths relative to its CWD, `$ZYNTHIAN_DIR/zynthian-webconf`). If `cert/cert.pem`/`cert/key.pem` don't exist, this raises and the process never comes up - not a soft failure. `cert/` is gitignored in the webconf repo itself (never shipped), and real hardware populates it via `zynthian-sys/sbin/regenerate_keys.sh` (`openssl req -x509 -newkey rsa:4096 ... -days 36500 -nodes -subj "/CN=$(hostname).local"`, at `$ZYNTHIAN_DIR/zynthian-webconf/cert/{key,cert}.pem`). **Decision**: both the Dockerfile (build time) and the new native script (first run) must generate this self-signed cert the same way before ever starting webconf - not optional, and there's no env var to disable the 443 listener. `run_zynthian_docker.sh` and the native script must therefore also publish/allow port 443 (or whatever `ZYNTHIAN_WEBCONF_PORT` fallback), not just the configurable HTTP port. `--cap-add=NET_BIND_SERVICE` (already planned) covers binding 443 too.
- **Dependency list was incomplete.** Beyond the proposal's list (`tornado`, `tornadostreamform`, `websocket-client`, `tornado_xstatic`, `terminado`, `xstatic`, `XStatic_term.js`), scanning every `import`/`from` in `zynthian_webconf.py` and `lib/*.py` turns up further packages not already covered by the Docker image's existing venv setup: `jsonpickle`, `mido`, `mutagen`, `py7zr`, `rarfile`, `requests`. (`JACK-Client` and `oyaml` are also imported but already installed via `zynthian-ui/requirements.txt`; `pyliblo3`/`beautifulsoup4` are already installed via the Dockerfile's existing extra pip step.) `bcrypt` was imported but entirely unused (dead import) in upstream's `security_config_handler.py` and was dropped by the login patch below - not needed. These new packages must be added to both the Dockerfile's venv install step and the native script's `pip install`.
- **`zyncoder`/`zynconf`/`zyngine`/`zyngui` imports**: `zynthian_webconf.py` does `sys.path.append(os.environ.get('ZYNTHIAN_UI_DIR'))` before importing `zyncoder.zyncore`, and `lib/*.py` handler modules go on to import `zynconf`, `zyngine`, and `zyngui` directly - i.e. webconf runs *in-process* against a chunk of `zynthian-ui`'s own codebase, not as an isolated service. This already works for free in this project's Docker image (`$ZYNTHIAN_UI_DIR` is set, `zyncoder` is already built and symlinked into it) and will work for the native install the same way, since both environments already have a working `zynthian-ui` checkout with `ZYNTHIAN_UI_DIR` set. No extra work needed here beyond what's already true of the existing setup - but it does mean webconf isn't safely startable without a working `zynthian-ui` install next to it (true in both our environments, just worth naming as a coupling).
- **Repo branch**: no fork-specific customization found; upstream `zynthian/zynthian-webconf` default branch is fine, no need to pin a fork like `zynthian-ui`'s `vangelis` branch.

## New Open Question: PAM/root login is a hard gate, not cosmetic (unresolved - needs a decision before implementation continues)

Every functional page in webconf is wrapped in `@tornado.web.authenticated` (confirmed across `dashboard_handler.py`, `engines_handler.py`, `midi_config_handler.py`, `audio_config_handler.py`, etc.) and login (`lib/login_handler.py`) works by PAM-authenticating **the OS `root` account's password** (`auth.set_item(PAM.PAM_USER, "root")`, PAM service `"passwd"`) - there's no separate webconf-internal account system, and no way to reach any config page without passing that login. This matches real Zynthian hardware, which runs webconf as `root` via `systemd` (no `User=` in the unit) and ships a known default root password.

Neither of this project's environments currently satisfies that:
- **Docker**: the container runs as the host's non-root UID/GID by design (`run_zynthian_docker.sh`'s `--user "$(id -u):$(id -g)"`, chosen deliberately for Xauthority/bind-mount ownership reasons). A non-root process generally can't PAM-authenticate against `/etc/shadow` at all, and the base Ubuntu image's `root` account has no password set (locked), so login would fail even if the process *could* read shadow.
- **Native**: `/zynthian` is owned by the invoking user, not run as `root`, and this machine's real `root` account password is the host's actual root password, not something to route through a dev tool's login form.

This is a real architectural fork, not a detail to default silently:
1. **Run webconf specifically as root inside the container** (e.g. a narrowly-scoped `sudo`/setuid path just for that one process, rest of the container stays non-root) **and set a documented default root password at build time** (mirroring real hardware's own "known default password, user should change it" convention). Native equivalent would mean starting the new script with `sudo`/as root and using *this machine's actual root password* to log in - not appealing for a dev script.
2. **Patch the login flow in the `zynthian-webconf` fork** (this project would need its own fork, like `zynthian-ui`'s `Famondir/zynthian-ui` fork, since there's no config knob to swap the auth backend) to accept a simple configured password instead of PAM/root - more upfront work (forking + patching + maintaining a delta against upstream) but avoids root entirely in both environments and is consistent with `CLAUDE.md`'s guidance that application-code fixes belong in a proper upstream-tracking fork, not hacked into this repo's Docker layer.
3. **Ship it unauthenticated-reachable only via a already-root context** - not applicable here since neither environment runs as root today.

No default is assumed here; this needs a decision from the change owner before tasks 2-6 (Dockerfile/entrypoint/native script/docs) are implemented, since the answer changes what those tasks actually do (add `sudo`+root password provisioning vs. add a fork+patch step).

### Decision (resolved and implemented)

Option 2: fork + patch. The fork already exists at `https://github.com/Famondir/zynthian-webconf`, branch `vangelis` (matching `zynthian-ui`'s fork/branch convention exactly), and was identical to upstream `zynthian/zynthian-webconf` HEAD (`7c229b3`) before patching.

Implemented as commit `7e7d4dc` on that branch:
- `lib/login_handler.py`: PAM/root auth replaced with a constant-time check (`hmac.compare_digest`) against `ZYNTHIAN_WEBCONF_PASSWORD` (read the same way `zynthian_webconf.py` already reads `ZYNTHIAN_WEBCONF_PORT`), keeping the existing `self.set_secure_cookie("user", "root", ...)` session mechanism as-is so every `@tornado.web.authenticated` handler downstream keeps working unmodified. If the env var isn't set, login is refused outright (no silent any-password-accepted fallback).
- `lib/security_config_handler.py`: the module-level `import PAM` (and the unused `import bcrypt`) removed - upstream's `update_system_config` also PAM-re-authenticated and rewrote the system/VNC/WIFI-hotspot/filebrowser passwords, none of which apply here. The password-change sub-flow now returns an explicit "not supported here, use `ZYNTHIAN_WEBCONF_PASSWORD`" error instead; hostname editing and `REGENERATE_KEYS` are untouched.

Both the Dockerfile and the native script clone `Famondir/zynthian-webconf` (branch `vangelis`) instead of upstream, mirroring exactly how `zynthian-ui` is already cloned from `Famondir/zynthian-ui`/`vangelis` in `docker/Dockerfile`.

This also resolves the self-signed cert step (still required, unrelated to the login patch - task-list item, not a design change) and keeps both environments fully non-root, consistent with the container's existing security model. A default `ZYNTHIAN_WEBCONF_PASSWORD` (documented, expected to be changed) will be set by `docker/entrypoint.sh` and `run_zynthian_webconf.sh`, the same "known default, override it" convention `JACKD_OPTIONS`/`NOVNC_BIND` already use elsewhere in this repo.

### Follow-on decision: native port binding uses `authbind`, not `setcap`

The Docker side's `--cap-add=NET_BIND_SERVICE` has no direct native equivalent - there's no per-process capability grant available from a plain shell script. The obvious-looking alternative, `setcap cap_net_bind_service=+ep` on the venv's `python3`, was rejected after checking: `/zynthian/venv/bin/python3` is a symlink to `/usr/bin/python3` (confirmed on this machine), and `setcap` follows symlinks - it would grant the capability to the *system* Python interpreter, letting any Python process on the machine bind privileged ports, not just webconf. Running the whole process as root via `sudo` was also rejected as reopening the exact root dependency the login patch above exists to avoid.

`run_zynthian_webconf.sh` instead requires `authbind` (a small, standard, widely-packaged tool for exactly this - letting a non-root process bind specific low ports it's been explicitly granted) as a documented prerequisite, checked at script startup with a clear error and the one-time `sudo touch/chown/chmod /etc/authbind/byport/{80,443}` setup command if missing - the script itself never calls `sudo`. `zynthian_webconf.sh` is launched via `authbind --deep`.

### Second bug found during live native testing (task 6.5): `get_i2c_chips()` crashes at import time

After authbind was set up, a live run of `run_zynthian_webconf.sh` on this machine got past login-related concerns entirely (port binding worked) but crashed on startup with a different error: `lib/wiring_config_handler.py` calls `DashboardHandler.get_i2c_chips()` **at module import time** (a bare `for i2chip in DashboardHandler.get_i2c_chips():` at module scope, not inside a function/handler), and that method shells out to `i2cdetect -y 1` unconditionally to scan for known Zynthian GPIO expansion boards (MCP23008/17, ADS1115, MCP4728). No desktop VM/container/laptop has `i2cdetect` installed or a real `/dev/i2c-1` bus, so this raised an unhandled `CalledProcessError` and killed the whole process before it ever got to serving a page - a second, unrelated real-hardware assumption baked into upstream, same category of issue as the PAM/root login one but orthogonal to it.

Fixed the same way `get_temperature()`/`get_volume_info()` elsewhere in that same file already handle missing hardware: wrapped the `i2cdetect` call in try/except, returning an empty chip list on failure instead of propagating. Committed as `a6addce` on `Famondir/zynthian-webconf`'s `vangelis` branch (on top of the login patch, `7e7d4dc`). No new dependency needed (didn't install `i2c-tools`) - the fix just makes absence tolerable, matching the file's existing convention, rather than faking hardware presence.

A broader scan for other module-import-time hardware probes across `lib/*.py` (the same technique used to find the original PAM/dependency list) found nothing else at import time that isn't already defensively wrapped (`audio_config_handler.py`'s RPi-version try/except already handles `RBPI_VERSION_NUMBER` being unset; `zynthian_config_handler.py`'s `liblo.Address(...)` just constructs an address struct, no I/O). Handler methods that run hardware `check_output` calls *lazily*, on request (visiting a specific settings page), aren't fixed here - out of scope for "webconf starts and login works," revisit if a specific page is found broken during actual use.

### Third bug found during live native testing (tasks 6.5/6.6): dashboard page itself crashed after login

With webconf starting cleanly, login succeeded (302 + cookie set) but the authenticated dashboard page (`GET /`) still 500'd. Root cause, found from the pasted traceback: `templates/dashboard_block.html` checked `'value' in info` (and `'value' in i` in a second spot) to decide whether to render a dashboard field - true even when the *value itself* is `None` (e.g. `DISPLAY_NAME`, built from `os.environ.get('DISPLAY_NAME')`, which is unset on this desktop install). Two call sites hit this: `escape(info['value'])` in the main HARDWARE/SYSTEM/MIDI & UI/etc. grid, and `urllib.parse.quote(i['value'])` in the dashboard's pre-filled "Report Issue" GitHub link (four separate loops there, same bug, all four fixed). `config_block.html` elsewhere in the same repo already uses the correct `info.get('value') is not None` check - this brings `dashboard_block.html` in line with that existing convention. Fixed in `f9effdf` and `820fccd`.

After both fixes, the dashboard renders correctly (confirmed via a live screenshot from the user) - HARDWARE/SYSTEM/MIDI & UI/SOFTWARE/LIBRARY/NETWORK panels all populate, login flow works end to end. One display quirk noted but **not a bug**: the dashboard's "Audio" field showed a stale soundcard name from a previous session, because `zynthian_webconf.sh` (via `zynthian_envars_extended.sh`) re-sources `$ZYNTHIAN_CONFIG_DIR/zynthian_envars.sh` (the system's last-*saved* audio config) after `run_zynthian_webconf.sh` already exported `SOUNDCARD_NAME` from `zynthian_envars_custom.sh` (the user's static override) - `zynthian_envars.sh` wins since it's sourced later. This is pre-existing Zynthian config-layering behavior (last-applied config vs. live hardware), not something this change introduced or needs to fix.

Native verification (tasks 6.5/6.6) is now complete: idempotent provisioning, authbind port binding, login, and the dashboard all confirmed working end to end on this machine.
