## Context

`fix-audio-hotplug-support` (archived) solved ALSA-card-level hotplug: a USB audio interface appearing/disappearing from `/proc/asound/` triggers `zynautoconnect`'s `start_alsa_in`/`start_alsa_out` bridging. The two gaps this change investigates are different signal paths entirely, not smaller versions of the same problem - initial checks on the reference machine already narrow both down further than the original "note, don't fix" task assumed:

**3.5mm jack** - `amixer -c sofhdadsp controls` shows the onboard codec already exposes ALSA jack-detection kcontrols: `Mic Jack`, `Headphone Jack`, `Speaker Phantom Jack` (plus 3 HDMI/DP jack controls). So the earlier assumption written into `fix-audio-hotplug-support/design.md` - "the onboard codec doesn't disappear/reappear from ALSA when a cable is plugged into its jack" - is true but incomplete: there's no *card*-level hotplug event, but there *is* a kernel/ALSA-level jack-sense signal available (a control-value-changed notification on these kcontrols, the same mechanism `alsamixer`/`amixer` would show updating live on insertion). `zynautoconnect.py` currently only reacts to card add/remove (via its existing hotplug polling) - it doesn't listen for ALSA control-change events at all, for any card. This is a real, own investigation track: whether `zynautoconnect`'s hotplug detection can also listen for control-change notifications (e.g. via `pyalsa`/`alsaaudio`'s control-notify APIs, or `alsactl monitor`-style polling) and treat a jack-insertion event on these kcontrols similarly to a card hotplug event for the purpose of prompting/activating the capture port.

**Bluetooth** - `run_zynthian.sh` stops `wireplumber`, `pipewire-pulse`, and `pipewire` themselves for the whole session (`systemctl --user stop ...`, restarted on exit) - this is the *only* audio-routing stack present on this machine capable of carrying BlueZ's Bluetooth audio profiles (A2DP/HFP) into anything else. `bluealsa` (the lower-level BlueZ-to-ALSA bridge that doesn't depend on PipeWire) is not installed on the reference machine. So a paired Bluetooth device's audio has no path to ALSA or JACK at all while Zynthian is running - not a bug in the hotplug bridging, but the direct, expected consequence of a design decision `zynthian-desktop-runtime` already made (stop PipeWire so jackd has exclusive access to the hardware). This matches what was observed live (AirPods mic+speaker registered nothing).

## Goals / Non-Goals

**Goals:**
- Determine, concretely, whether the 3.5mm jack's kcontrol-based jack-sensing can be wired into `zynautoconnect`'s existing hotplug-triggered port-activation path, and estimate the effort/risk of doing so.
- Determine, concretely, whether Bluetooth audio can be bridged into JACK without reintroducing the PipeWire/jackd device conflict `zynthian-desktop-runtime` already solved by stopping PipeWire (the `bluealsa-aplay`-into-a-loopback-card idea is the leading candidate, not yet verified) - or confirm it can't be done cleanly and should be documented as a permanent limitation instead.
- Produce a clear per-source decision (fix now / fix later / permanent limitation) with the reasoning recorded, so this isn't re-investigated from scratch next time it comes up.

**Non-Goals:**
- Implementing either fix as part of this change - that's a follow-up `/opsx:apply` (or a fresh proposal) once the investigation lands on "worth fixing".
- Changing anything about the Docker image - it has no host PipeWire to stop and no onboard-jack passthrough path in the same sense (no `/dev/snd` jack-sensing across a container boundary has been explored at all).
- Re-litigating the PipeWire-stop decision itself (`zynthian-desktop-runtime`'s existing, working trade-off) - any Bluetooth bridge has to work *around* that decision, not replace it.

## Decisions

### 3.5mm jack (resolved by tasks 1.1-1.4)

**Confirmed real and reliable.** `Mic Jack`/`Headphone Jack` (numid 11/12 on `hw:sofhdadsp`) genuinely flip on physical insertion/removal (live-tested: insertion showed `Headphone Jack` then `Mic Jack` transition ~0.4s apart, matching sequential TRRS contact engagement; removal flipped both back). `numid=13` ("Speaker Phantom Jack") is a red herring - a fixed `on` "phantom" control (no real sense pin for the built-in speaker output) and must be excluded, not treated as a hotplug source.

`zynautoconnect.py`'s existing hotplug detection (`auto_connect_thread()`) is already a plain ~2s polling loop, not event-driven - so wiring this in needs no new dependency (`pyalsa`) or event-subscription machinery; a subprocess `amixer -c sofhdadsp cget numid=11/12` check fits directly into the existing cycle. Targeted numid reads are inherently unambiguous (no diffing against the full control set), so no false-positive risk from unrelated control changes (volume, etc.).

**Important reframing found during investigation**: this is a smaller and *different* feature than "hotplug bridging" in the `alsa_in`/`alsa_out` sense `fix-audio-hotplug-support` implemented. A USB device's ALSA card (and its PCM devices) appear/disappear - there's a real *card* to bridge in or tear down. The onboard codec's mic-in PCM device (and its JACK port) exists *permanently*, regardless of jack-sense state (confirmed live via `jack_lsp` - the onboard mic capture port is always present in the graph). Jack-sensing doesn't create or destroy anything at the ALSA/JACK level; it only tells you whether something is *actually plugged in* right now. So "wiring this in" means: gating whether that always-present port is offered/auto-connected as an active input (e.g. don't auto-route a chain to a floating, unplugged mic input) and refreshing that gate on the same ~2s cycle - not a bridge-process lifecycle like `start_alsa_in`/`start_alsa_out`.

**Decision: worth implementing.** Low effort (a few lines added to the existing polling loop, no new dependency), mechanism fully de-risked by this investigation, and it closes a real, confirmed gap. Scope: jack-presence-aware capture-port gating in `zynautoconnect.py`, not full ALSA-card hotplug bridging. Not implemented here (see Non-Goals) - needs its own follow-up change.

### Bluetooth (resolved by tasks 2.1-2.5)

**Confirmed zero ALSA-level footprint without `bluealsa`.** Live-tested with the actual paired AirPods: even while actively connected, they never appear in `aplay -l` - only via PipeWire's own `bluez5` module (`wpctl status`), regardless of whether PipeWire is running or stopped. Matches the original hypothesis exactly.

**`bluealsa` (`bluez-alsa-utils` package) bridges this, confirmed audibly.** Installed, connected the AirPods fresh with PipeWire stopped (a PipeWire-held BT connection drops when PipeWire stops, and PipeWire/bluealsa both try to claim the same BlueZ A2DP media endpoint - only one can hold it at a time, consistent with `zynthian-desktop-runtime`'s existing PipeWire-stop trade-off). `bluealsa-aplay -L` then listed a real PCM (`bluealsa:DEV=...,PROFILE=a2dp`, SBC 48kHz stereo), and direct playback through it was audibly confirmed by the user.

**The existing `alsa_out`/`alsa_in` bridge binaries (`fix-audio-hotplug-support`'s own mechanism) crash outright on a bluealsa device string** - reproducible `buffer overflow detected` abort, not an environment issue (works fine with plain `hw:` strings). Routing through an intermediate `snd-aloop` card instead works cleanly: a plain `arecord | aplay` pipe moved real, audibly-confirmed audio between the Loopback card and bluealsa, and `zynautoconnect` already treats `Loopback` as a normal device via its existing polling (no changes needed there).

**Follow-up: the ~500ms extra buffering was avoidable, tested and confirmed.** Re-ran the bridge with explicit small buffer/period sizes (`arecord`/`aplay -F 20000 -B 40000`, 20ms period / 40ms buffer instead of the untuned ~500ms default) - `bluealsa-pcm`'s own log confirmed the requested size took effect ("Selected HW buffer: 2 periods x 3840 bytes == 7680 bytes", i.e. 40ms). Played a 4-tone sequence (440/660/880/550Hz, live-generated with `sox` after an initial `sox` chaining mistake was caught and fixed) through the tuned bridge - user confirmed all four tones came through cleanly and distinctly, no crackling during playback, only a minor click at the very end of the last tone (a normal abrupt-stream-stop artifact at tiny buffer sizes, not evidence of underrun during playback - no xruns were logged). This gets the *bridge's own* contribution down close to negligible, leaving the ~150ms AVDTP floor as the dominant remaining cost.

**Decision (unchanged): document as a permanent limitation for live/real-time musical use, not worth implementing.** The blocker isn't feasibility (the bridge works, tunes well, and is simpler to build than the jack fix - no upstream patch needed) - it's the ~150ms AVDTP transport delay (`Delay: 0x05dc`, units of 1/10ms) BlueZ itself reports, which is a hard A2DP/SBC protocol floor no amount of bridge tuning can remove. Even with the bridge's own latency tuned down to near-nothing, ~150-190ms total is still well past the point (~20-30ms) where a live-monitoring round trip feels disruptive rather than instant. This is exactly the risk design.md's original "Risks" section flagged as a real possibility before investigation started - confirmed, not just assumed.

## Risks / Trade-offs

- The jack-sensing kcontrol approach adds a second, different "something changed" signal type to `zynautoconnect` (control-notify, not card add/remove) - worth checking whether this fits its existing polling loop cleanly or needs a genuinely separate code path, since that affects how much this is really "extending" vs. "duplicating" the hotplug mechanism.
- A `bluealsa`-based Bluetooth bridge would be a new runtime dependency and a new moving part (BlueZ pairing state, `bluealsa` service, the loopback card, latency of the extra hop) on top of an already iteration-heavy audio stack (`zynthian-desktop-runtime`'s own history) - even if technically possible, worth weighing against just documenting the limitation, especially if Bluetooth audio quality/latency through such a bridge turns out to be poor for live playing.
- Both investigations depend on state specific to this reference machine (this exact codec's kcontrol names, this exact absence of `bluealsa`) - findings should be treated as "true on this machine" unless cross-checked against other hardware, matching the same caution `fix-audio-hotplug-support` applied to `JACKD_OPTIONS`.
