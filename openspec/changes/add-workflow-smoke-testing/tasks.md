## 3. Log-diff assertion

- [x] 3.1 Implement per-step log tail capture + diff: mark the tail position before a step, inject, poll (bounded timeout, not a fixed sleep) for the log to stabilize, then diff for new `ERROR`-level/traceback lines. Implemented in `workflow_testing/log_diff.py`. Verified against a synthetic log file reproducing the exact `enable-webconf-access` pattern (pre-existing harmless `i2cdetect`/boot `ERROR` lines correctly ignored since they're outside the diff window; a genuine new `Traceback`+`ERROR` pair correctly flagged, real concurrent writer thread, bounded-timeout stabilization confirmed working).
- [x] 3.2 Confirm this catches a real regression against the actual live system (not just the synthetic reproduction from 3.1): temporarily reintroduce one of `enable-webconf-access`'s fixed bugs (or an equivalent zynthian-ui-side crash) and verify a workflow step correctly fails on it, then revert. Done live against a real native session (see group 4): a deliberate guard clause was added (on the wrong screen name and never actually triggered), but the log-diff mechanism caught something better - a genuine, pre-existing regression: injecting `SCREEN_MIDI_RECORDER` crashed with `FileNotFoundError: .../files/Midi` (that directory was never scaffolded, on either native or Docker). Fixed both (see `docker/entrypoint.sh` and the native `zynthian-my-data` tree directly), re-ran the same injection, confirmed `assert_no_new_errors` now passes. Deliberate guard clause reverted (never fired, since the real screen name is `midi_recorder` not `audio_recorder`).
- [x] 3.3 (found while building the shared runner, ahead of group 7) Implement the shared step-execution core (`workflow_testing/runner.py`, design.md's "Shared step-execution core" decision): YAML workflow loader, per-step CUIA injection + `no_new_errors` (unconditional) + optional `screen_is` assertion, workflow-level `save_snapshot`/`assert_zss`/`reload_and_check_audio` hooks (the latter two still raise `NotImplementedError`, pending 6.1b/6.2). Two real bugs found and fixed live while validating it end-to-end against the native adapter:
  - `PYTHONUNBUFFERED` was missing from both adapters' launched-process environment - block-buffered (non-TTY) stdout/stderr meant log lines could be *flushed* to the file well after they were *generated*, misattributing old, harmless content to a later step's diff window. Fixed in both `native_adapter.py` and `docker_adapter.py`.
  - `screen_is` assertions only checked for a *fresh* `SHOW SCREEN '<name>'` line in the step's diff window - but `show_screen()` only logs on an actual change (`if self.current_screen != screen:` guard), so a step whose target screen is already current (e.g. `SCREEN_MIXER` right after boot, which already defaults to mixer) is a legitimate no-op and produces no fresh line, false-failing the assertion. Fixed by tracking last-known current screen (seeded from the log once at session start, updated per step) instead of requiring a fresh line every time.
  - Separately (not a bug in this module, but a real app-behavior finding): injecting `SCREEN_CHAIN_MANAGER` as the very first navigation right after boot doesn't land there - it triggers the chain's FluidSynth engine to lazily start (several seconds of soundfont/preset loading) and ends up back on `mixer` instead, while also re-running the same Bluetooth "no controller configured" check boot already ran once. That check was wrongly logged at ERROR level (fixed on the fork, see below) which made this look like a regression; the screen-landing behavior itself is real and workflows should account for it (e.g. don't assert `screen_is: chain_manager` as the immediate first step of a fresh session).

## 6. Structural and round-trip assertions

- [x] 6.1a Implement the JSON-based structural assertion helper (`assert_chain_has_engine`, `assert_chain_count`) against `chains`/`slots` content. Implemented in `workflow_testing/zss_assert.py`, verified against a real `.zss` on this machine (`/zynthian/zynthian-my-data/snapshots/default.zss` - confirmed chain count, FluidSynth engine code present/absent detection, missing-file handling all correct).
- [x] 6.1b Implement `save_snapshot` (trigger a save via CUIA, locate the resulting `.zss` in the session's `zynthian-my-data/snapshots`) - needs a live session to confirm which CUIA triggers a save and where it lands, deferred. Resolved live: saving isn't a single CUIA - the `snapshot` screen's "SAVE" list entry (`zyngui/zynthian_gui_snapshot.py`) opens an on-screen keyboard pre-filled with "New Snapshot", defaulted to the "Enter" key. Implemented as `runner.save_snapshot()`: `SCREEN_SNAPSHOT` -> `SELECT 0` (highlight the list's first entry, no confirm) -> `SELECT_ACTION 'S'` (confirm) -> `SELECT_ACTION 'S'` again (confirms whatever came up next - the keyboard's "Enter", or an options-menu default, depending on the session's existing snapshot-bank state, see below). Two new CUIA-level `CuiaInjector` methods (`select_list_item`, `confirm_selection`) and 3 new allow-listed CUIAs (`SCREEN_SNAPSHOT`, `SELECT`, `SELECT_ACTION`) - see design.md for why these are still safe despite being generic "confirm the highlighted item" actions.

  Found live: the exact list position index 0 lands on - and therefore the resulting save path - depends on what's *already* in the target session's snapshot banks. This project's own long-reused native install (many banks/snapshots accumulated from a full day's testing) landed on a "Last State" entry instead of "SAVE", saving to `last_state.zss` via an options-menu confirm; a genuinely fresh Docker scratch `my_data_dir` landed on the real "SAVE" entry, saving to `snapshots/000/001-New Snapshot.zss` via the keyboard flow. Rather than assume either path, `save_snapshot()` parses the actual path from `zynthian_state_manager.save_snapshot()`'s own `"Saving snapshot <path> ..."` log line - correct regardless of which internal path the confirm sequence happened to trigger. Verified live and reproducibly in both environments (fresh, different, correct paths each time; correct structural content via 6.1a's assertions).
- [x] 6.2 Implement `reload_and_check_audio`: start a fresh session (either environment) that loads the just-saved `.zss` as its default snapshot, inject a note, confirm non-silent audio via the existing `jack_rec`+`sox` technique. Implemented in `runner.py`, using a self-contained VMPK start/stop (native_adapter/docker_adapter don't manage VMPK themselves - out of scope for ordinary structural/log-diff workflows). Docker needs `docker_adapter.launch()`'s new `my_data_dir` parameter (reuse the original session's snapshot directory instead of a fresh empty one - required a `DockerSession` lifecycle fix so tearing down the original session doesn't delete data the reload session still needs) and `--device /dev/snd`/`--group-add audio` (VMPK runs on the *host*; without host ALSA-seq passthrough into the container, `a2jmidid` there can never see it - same flag `test_zynthian_docker.sh` already validated for this exact purpose; doesn't compromise the dummy-driver isolation, `JACKD_OPTIONS` stays `-d dummy` regardless). Also sets `ZYNTHIAN_MIDI_BLE_ENABLED=0` in the Docker adapter's scratch config (found live: this container has no systemd at all, so `default_bluetooth()`'s `systemctl start bluetooth` attempt fails loudly at ERROR level whenever `bluetooth_enabled` is left truthy - the native install's own config sets this to `1` instead, safe there only because real systemd/a real `bluetooth.service` are present to short-circuit before ever reaching that failing command). **Fully verified live end-to-end in both environments** (real captured audio, RMS above the silence threshold, via `test_workflow4.yaml`-style workflows run against both adapters against the same freshly-rebuilt image).

Real bug found and fixed live while validating this: injecting a note immediately after VMPK's window appears produced silent audio - `zynautoconnect`'s hotplug auto-connect thread polls for new MIDI ports on a ~2s cycle (`zynautoconnect.py`'s `deferred_timeout`), not instantly, so the very first `jack_rec` capture ran before VMPK's bridged port was actually wired into the signal path (confirmed via `jack_lsp -c` showing zero connections on it at that point). Fixed by adding `list_port_connections()` to both session types and polling (bounded timeout, not a fixed sleep) until `ZynMidiRouter:dev0_in` shows a connection before playing the note - see `runner._wait_for_vmpk_autoconnect()`.

## 7. Starting workflow library

- [x] 7.1 Workflow: build a FluidSynth-based chain from scratch (navigate to chain manager, add chain, select FluidSynth engine, confirm active) - the ported equivalent of `test_zynthian_docker.sh`'s single scenario, now built live instead of loaded from a fixture. Implemented as `workflow_testing/workflows/build_fluidsynth_chain.yaml`. Required extending `Step`/the YAML schema with four new action kinds beyond `screen`/`zynswitch` (`cuia`, `select`, `confirm`, `arrow`) plus matching `CuiaInjector` methods and allow-listed CUIAs (`ADD_CHAIN`, `ARROW_RIGHT`/`ARROW_LEFT`) - the add-chain wizard needs a bare CUIA jump, list navigation, and a category-tab switch that `screen`/`zynswitch` alone couldn't express. The exact FluidSynth-selection sequence was found live, not guessed: the engine screen opens on a "Synth" category listing 28 LV2/JALV-hosted synths (several of which crash outright on this machine - `KeyError: Plugin not found`, a pre-existing, unrelated LV2-plugin-registry gap left uninvestigated, out of scope here); one `ARROW_RIGHT` switches to the "Sampler" category, where FluidSynth is the first entry. **Fully verified live end-to-end in both environments**, including `save_snapshot`/`assert_zss`/`reload_and_check_audio` (real captured audio) - critically, in Docker starting from a genuinely empty scratch `my_data_dir` (no pre-existing snapshot at all), the actual "from scratch" case this task asks for, not just a reused/pre-populated one.

  Two more real bugs found and fixed live while running this longer, more realistic workflow end-to-end:
  - `reload_and_check_audio`'s `default.zss` copy was derived from `zss_path`'s own parent directory - wrong whenever `save_snapshot()` lands inside a numbered bank subfolder (`snapshots/000/...`, the normal case for a fresh install) rather than directly in the top-level snapshots dir; `default.zss` written into the bank subfolder is never found at boot (`zynthian_state_manager.default_snapshot_fpath` is always the top-level path). Fixed by always targeting `session.snapshots_dir` explicitly instead of guessing from `zss_path`.
  - For a Docker session that owns its own scratch `my_data_dir` (the normal, non-override case), `run_workflow()`'s existing "tear down before reload" step (task 6.2) deleted that whole directory - including the `default.zss` just written into it - before `reload_and_check_audio()` ever got to reuse it. Even worse, the resulting *nonexistent* path handed to the reload's own `docker run -v` wasn't rejected: dockerd (real root) silently auto-created it as an empty, root-owned directory instead, producing a confusing, seemingly-unrelated "Permission denied" crash deep in that session's boot log. Fixed two ways: `run_workflow()` now disarms the original session's `my_data_dir` ownership right before tearing it down (transferring responsibility to the reload flow, an accepted small leak rather than auto-deleting data about to be reused), and `docker_adapter.launch()` now refuses outright (clear `FileNotFoundError`) if a passed `my_data_dir` doesn't already exist, instead of letting Docker paper over it silently.
- [x] 7.2 Workflow: add an amp-simulator effect to an existing chain. Found and fixed a real, previously-broken app bug along the way: the `CHAIN_OPTIONS` CUIA (needed to reach a chain's "Add Audio-FX processor" action) called a nonexistent `.setup()` method on the chain-options screen - `AttributeError` on every single use, entirely broken before this.
