## Context

Three things already exist and this design builds directly on them rather than re-inventing:

- `test_zynthian_docker.sh` / the `docker-smoke-testing` capability: proved a private Xvfb display + VMPK (via a2jmidid) + `snd-aloop` + `jack_rec`-against-the-mixbus is enough to headlessly boot the Docker image, inject a real MIDI note, and confirm audio without a human. Its own `design.md` (archived at `openspec/changes/archive/2026-09-23-docker-automated-smoke-test/`) already worked through and solved several sharp edges this change reuses verbatim: `arecord` against `snd-aloop`'s capture side is unreliable (`EIO` on read) - use `jack_rec` against the mixbus instead; a committed fixture snapshot needs a soundfont path that exists in the target environment, which is exactly the class of problem live-building state (this change's core idea) avoids structurally.
- `support-virtual-test-devices` / `setup_virtual_devices.sh`: proved VMPK + `snd-aloop` work identically on the native install, not just Docker - MIDI reaches the active chain via `a2jmidid` with no manual `jack_connect`, confirmed live on this machine.
- `run_zynthian_vnc.sh`: proves a fully headless Xvfb display is enough to run the real Tk GUI natively, the same technique `test_zynthian_docker.sh` already uses for Docker.

New for this change, found during exploration: `zyngine/zynthian_state_manager.py` (~line 812) maps MIDI note-on/note-off on the configured "master MIDI channel" directly to CUIA (Callable UI Action) dispatch, via `zynthian_gui_config.master_midi_note_cuia` - defaulting (no config needed) to `zynconf.NoteCuiaDefault` in `zynconf/zynthian_config.py`: notes 90-118 map to `ZYNSWITCH 0` through `ZYNSWITCH 28` (all virtual encoder/button switches), with **note-on = press, note-off = release** - the real time gap between them runs through the same `zynswitch_bold_us`/`zynswitch_long_us` (300ms/2000ms defaults, `zyngui/zynthian_gui_config.py`) threshold logic that classifies real hardware presses into short/bold/long. Notes 60-77 map to direct `SCREEN_*` jumps (`SCREEN_CHAIN_MANAGER`, `SCREEN_ADMIN`, `SCREEN_MIXER`, etc.). This is reachable through the exact same VMPK→a2jmidid MIDI path already proven for both environments - no new remote-control surface needs to be added to `zynthian-ui`.

`.zss` snapshot files (`$ZYNTHIAN_MY_DATA_DIR/snapshots/*.zss`) are plain JSON (`schema_version`, `chains` with `slots` referencing engine codes like `"FS"` for FluidSynth, `zs3` for scenes) - confirmed by reading a real snapshot on this machine. Directly parseable/assertable without booting anything.

## Goals / Non-Goals

**Goals:**
- One shared mechanism that drives workflow scripts against *either* native or Docker sessions, so adding a new workflow automatically covers both - not two independently-maintained scripts.
- Replace `test_zynthian_docker.sh`/`docker-smoke-testing` outright (see proposal's BREAKING note) rather than keep it running alongside the new system.
- A small, real starting library of workflows (build a FluidSynth chain, add an amp-sim effect, set up MIDI recording), designed to keep growing - each new workflow is a script addition, not new engine code.
- Three complementary assertion layers (log-diff, structural `.zss` check, round-trip reload) usable per-step or per-workflow as appropriate, not just "screenshot non-blank + one audio check" as today.
- A safety deny-list preventing automated runs from ever triggering `POWER`, `RESTART_UI`, or admin-screen-reachable reboot/update/factory-reset actions.

**Non-Goals:**
- Hosted CI integration - unchanged from the capability this supersedes; still a locally-triggered dev tool (no `/dev/snd`/X11/`audio`-group on a typical CI runner).
- Pixel-perfect visual regression testing - screenshots (if used at all) stay a "did something render" check, not a golden-image diff.
- Exhaustive fuzzing of every switch × duration × screen combination - explicitly considered during exploration and rejected in favor of deliberate, hand-designed workflow scripts (real usage patterns, not random input coverage). Could be a cheap future addition on top of the same injection mechanism, but out of scope here.
- Testing `zynthian-webconf` (a completely different technique - HTTP, not MIDI/GUI) - deferred, not part of this change.
- Real-hardware-specific validation (physical Suprema, physical switches) - unchanged Non-Goal from the capability this supersedes.

## Decisions

### Shared step-execution core, thin per-environment adapters
The workflow *definitions* (ordered list of steps: MIDI CUIA injection + assertion) live in one place and are environment-agnostic. Only two things differ per environment, both already solved by existing scripts:
- **Launch/teardown**: native uses a private Xvfb display (`run_zynthian_vnc.sh`'s technique); Docker uses a headless container (`test_zynthian_docker.sh`'s technique, `docker run -d --name ... zynthian-desktop:latest`).
- **Audio capture for the round-trip check**: Docker uses `jack_rec` via `docker exec` against the container's own JACK graph (already solved, see Context); native runs `jack_rec` directly on the host, no `docker exec` indirection needed - actually simpler than the Docker case.

This directly answers the user's "muss nativ und docker synchron halten" requirement: a new workflow script is written once and runs against both by construction, rather than needing a matching native port authored separately each time.

### CUIA/switch/screen steps via direct OSC, not VMPK/MIDI at all; VMPK/MIDI stays only for musical-note audio verification
**Corrected twice during this task, converging on a better answer than either original plan.** First draft assumed `xdotool key` against VMPK (based on `docker-automated-smoke-test`'s design doc without re-checking its shipped implementation - that script's own comment documents `xdotool key` producing *zero* MIDI events, confirmed live with `aseqdump`; the working technique there is mouse click-and-hold on VMPK's on-screen piano, derived from window geometry). Re-deriving click coordinates for the *specific* notes this change needs (90-93, 60/64/69, 12 - not just "one arbitrary visible note" like the existing script) would have needed live pixel calibration with real risk of window-size/layout fragility.

Found something better while confirming the timing-classification mechanism: `zyngui/zynthian_gui.py` runs a real OSC server (`zynconf.ServerPort["cuia_osc"]`, port 1370) whose catch-all handler (`osc_cb_all`) dispatches `/CUIA/<name> <args...>` messages straight into the same `cuia_queue` the MIDI-note path uses (`zyngui/zynthian_gui.py` ~line 427). `cuia_zynswitch(params)` reads `params[0]` (switch index) and `params[1]` (`'P'`/`'R'`) exactly the same way regardless of whether the queue entry came from a MIDI note-on/off or an OSC message - confirmed by reading the queue consumer (~line 2771: `zynswitch_cuia_ts[i] = monotonic()` on `'P'`, elapsed-time-based `zynswitch_timing(dtus)` classification on `'R'`, using the same `zynswitch_bold_us`/`zynswitch_long_us` thresholds either way).

**Decision**: use direct OSC (`liblo`/`pyliblo3`, already a proven dependency in this project's venvs) to send `/CUIA/ZYNSWITCH <i> P` then, after the target hold duration, `/CUIA/ZYNSWITCH <i> R` for switch-press steps, and a single `/CUIA/SCREEN_<NAME>` message for direct screen jumps. This needs no VMPK process, no Xvfb window-geometry math, no pixel-coordinate calibration at all for these steps - eliminates the task 2.1b blocker entirely. VMPK (mouse-click technique, as already proven) is kept, but narrowed to only what it's actually needed for: injecting a real *musical* MIDI note on a chain's assigned channel during round-trip audio verification (`reload_and_check_audio`) - CUIA has no generic "play this note on this engine" message, and using real MIDI there is also the right level of fidelity (emulating what a musician's controller would send), unlike UI navigation.
- *Alternative considered*: routing switch/screen steps through MIDI+VMPK too, for uniformity with the audio-check path. Rejected - strictly worse on every axis for this specific use (fragile pixel coordinates, an extra process, no benefit) once OSC's exact push/release semantics were confirmed to match.
- *Alternative considered*: a Python MIDI library (`mido`) writing raw ALSA sequencer events for switch/screen steps too. Rejected as unnecessary now that OSC covers this need without touching MIDI/a2jmidid at all for these steps.

### Workflow scripts as an ordered list of (CUIA action, assertions) steps
Each step names one MIDI-injected action - either `zynswitch <i> <short|bold|long>` or a direct `screen <name>` jump - and the assertions to run immediately after it. Available assertions, composable per step:
- `no_new_errors`: diff the log tail before/after the step, fail on any new `ERROR`/`Traceback` line.
- `screen_is <name>`: optional, only where the expected resulting screen is worth pinning down (see Open Questions - exact mechanism for reading current screen from outside the process still needs to be nailed down during implementation).
- (workflow-level, not per-step) `save_snapshot` + `assert_zss <jsonpath-like-check>`: save state at the end of a workflow, parse the resulting `.zss`, assert on its `chains`/`slots` content.
- (workflow-level) `reload_and_check_audio`: the existing fixture-load-and-verify-audio mechanism, pointed at the just-saved `.zss` instead of a committed file.

### `no_new_errors` via per-step log tail diff, not a global allowlist
Rejected the originally-considered "maintain an allowlist of known-harmless ERROR lines" approach (`i2cdetect: not found`, `wlan0 not found`-style lines seen during `enable-webconf-access`'s manual testing) - an allowlist needs constant upkeep and a new harmless line silently added upstream would need a matching allowlist update before tests pass again. Comparing only the log lines emitted *during this one step* against zero tolerance is self-scoping: a pre-existing harmless startup warning is outside every step's diff window by construction (it happened once, at boot, before step 1's tail marker), so it never needs allowlisting at all.

### CUIA allow-list keyed by CUIA name, not MIDI note number
Since switch/screen steps now go over OSC directly (previous decision), the allow-list no longer needs to go through `NoteCuiaDefault`'s note-number translation at all - it's simply a set of allowed CUIA name strings (`ZYNSWITCH`, `SCREEN_CHAIN_MANAGER`, ...), checked against the OSC path about to be sent. One less moving part than the original MIDI-note-keyed design, and no dependency on the target session having `NoteCuiaDefault`/`master_midi_note_cuia` configured any particular way (that table is no longer consulted for switch/screen injection at all, only conceptually for reference when choosing which CUIAs exist).

### CUIA safety allow-list, checked before every injection
`NoteCuiaDefault` maps note 0 → `POWER`, note 4 → `RESTART_UI`, and several notes are direct `SCREEN_ADMIN`/etc. jumps from which further real switch-presses could reach reboot/software-update/factory-reset. The workflow engine SHALL refuse to inject any note whose mapped CUIA is not on an explicit allow-list (safer default than a deny-list, given how easy it'd be to miss one dangerous admin-reachable path) - workflow scripts can only use CUIAs the engine already knows are safe, new ones added deliberately as workflows need them, not discovered by accident during a run.

### `.zss` structural assertions via plain JSON parsing, no snapshot-schema library
Confirmed live (see Context) that `.zss` is plain JSON with a stable enough top-level shape (`schema_version`, `chains`, `zs3`) to assert against directly - `assert any(slot.get(k) == "FS" for slot in chain["slots"] for k in slot)`-style checks, no need for a schema-validation dependency. If `schema_version` itself changes in a future `zynthian-ui` update, structural assertions written against the old shape will fail loudly and visibly (a `KeyError`/assertion failure naming the workflow) rather than silently accepting a differently-shaped file - itself a useful regression signal, not just a maintenance cost.

### Removing `test_zynthian_docker.sh` and its committed fixture outright
Per the proposal's BREAKING note: rather than keep the old single-scenario script running alongside the new system (which would mean two independently-evolving test mechanisms, one of which only covers Docker), its one scenario becomes the first workflow script on the new engine and the old script/fixture are deleted. `docker/fixtures/smoke-test-default.zss` is no longer needed - workflows build and save their own snapshot, closing the exact soundfont-path staleness problem that fixture already hit once.

## Risks / Trade-offs

- **Live-building state per run is slower than loading a static fixture** → acceptable trade-off for the coverage/reliability gain (exercises real UI code paths, not just audio-signal plumbing); workflows can still `save_snapshot` partway through and a later, separate workflow could `reload` from an earlier workflow's saved output if reuse becomes worth optimizing for - not needed for the initial library.
- ~~Determining "did the UI reach the expected screen" without a new remote-introspection channel~~ → **resolved** (task 1.1): a one-line `logging.debug` patch to the `zynthian-ui` fork makes `screen_is` assertable via the same log-diff mechanism already needed for error detection.
- ~~VMPK click-position calibration for specific high MIDI notes~~ → **resolved, no longer applicable**: switchus/screen steps moved to direct OSC (see "CUIA/switch/screen steps via direct OSC" decision above), which needs no window/pixel calibration at all. VMPK is still used, but only for injecting a real musical note during round-trip audio verification - the same single-arbitrary-note use case `test_zynthian_docker.sh` already proved works, not the specific-note problem that prompted this risk originally.
- **The OSC server's bind address/reachability from a Docker adapter is unconfirmed** → `zyngui/zynthian_gui.py` constructs `liblo.Server(self.osc_server_port, self.osc_proto)` with no explicit bind address; native access (localhost) is unaffected, but reaching it from outside a Docker container (task 5.x) may need the same kind of port-publish handling `enable-webconf-access` already worked out for webconf's HTTP/HTTPS ports - confirm during task 5 implementation, not assumed here.
- **Deny/allow-list maintenance** → a workflow needing a CUIA not yet on the allow-list fails closed (refuses to inject) rather than failing open (injecting something unreviewed) - safe default, but means the initial allow-list needs to cover whatever the starting workflow library actually needs, checked explicitly during implementation rather than assumed complete.
- **Log-diff timing races** (log line for a given action arriving after the script's post-step check runs) → poll with a bounded timeout for the tail to stabilize (no new lines for N ms) rather than a fixed sleep, same class of fix already applied in `docker-automated-smoke-test`'s design for boot-sequencing races.

## Migration Plan

- Delete `test_zynthian_docker.sh` and `docker/fixtures/smoke-test-default.zss` once the new engine's ported version of that same scenario (fixture-free: build a FluidSynth chain live, connect it, inject a note, confirm audio) passes.
- Archive `docker-smoke-testing`'s spec with a `REMOVED Requirements` delta (Reason: superseded by `workflow-smoke-testing`; Migration: use the new engine's equivalent workflow script) rather than silently deleting the historical record.
- No data migration - purely dev-tooling.

## Open Questions (resolved during implementation)

### Screen introspection (task 1.1) - resolved

`zyngui/zynthian_gui.py`'s `show_screen()` fires `zynsigman.send(zynsigman.S_GUI, zynsigman.SS_GUI_SHOW_SCREEN, screen=screen)` on every screen change - but `zynsigman` is a purely in-process pub/sub system (Python callbacks only, used by control-device drivers like the Launchkey/Mackie/Akai integrations to react to screen changes), not externally observable. No OSC/websocket/log bridge exists for it. `close_screen()` (back-navigation) already logs `logging.debug(f"CLOSE SCREEN '{self.current_screen}' => Back to '{last_screen}'")`, but `show_screen()` (forward navigation/jumps) has no equivalent log line.

**Decision**: add one `logging.debug(f"SHOW SCREEN '{screen}'")` line to `show_screen()` in the `Famondir/zynthian-ui` fork, right next to the existing `zynsigman.send(...)` call, mirroring `close_screen()`'s existing pattern exactly. This is a single-line, low-risk addition to a fork this project already patches for desktop-port needs (same category as `enable-webconf-access`'s login patch on the webconf fork) - not a new remote-control surface, just a log line. `screen_is` assertions then run through the *same* log-diff mechanism (design's "Per-step log-diff assertion" decision) already being built for error detection - no second introspection mechanism needed. This slightly revises the proposal's Impact note ("no application code changes to zynthian-ui itself expected") - one minimal, additive log line is needed after all.

**Bug found live during task 3.2/4.1 validation**: `logging.debug()` never actually appeared in a live session's log - `ZYNTHIAN_LOG_LEVEL="20"` (`logging.INFO`) is the standard runtime level in both `zynthian_envars_custom.sh` (native) and the Docker image, which filters `DEBUG` out entirely. Changed to `logging.info()` on the fork; confirmed live afterwards that `SHOW SCREEN '<name>'` now appears at the level both environments actually run at.

### Native adapter avoids `run_zynthian.sh` entirely - dummy JACK driver, isolated server name

Task 4.1's launch technique deliberately doesn't reuse `run_zynthian.sh`/`run_zynthian_vnc.sh`, even though those already solve "boot zynthian-ui on a headless display": both stop the host's real PipeWire and bind jackd to real hardware (`JACKD_OPTIONS`) - correct for an interactive session, but disruptive for a scripted background test that (for most steps) only needs structural/log assertions, not real audio hardware. Instead `workflow_testing/native_adapter.py` starts jackd directly with the `dummy` driver under its own server name (`-n zynworkflow`, never the default), and `a2jmidid -j zynworkflown` scoped to match - confirmed live this never touches `/dev/snd` or PipeWire, so a workflow test can run concurrently with a real interactive session or unrelated host audio activity, with no PipeWire stop/start/restore step needed at all (a deliberate simplification versus the Docker adapter, task 5, which still needs `/dev/snd` passthrough for its own PipeWire handoff). `zynthian_envars_custom.sh` is still sourced (for `RBPI_VERSION`/`BLINKA_FORCEBOARD`/`LV2_PATH` etc. needed at Python import time - found live: without it, `zynthian_engine_jalv.py` crashes at import with `TypeError: argument of type 'NoneType' is not iterable` reading `RBPI_VERSION`), but its `JACKD_OPTIONS` is simply never used.

Two more bugs found live while validating this adapter, both fixed directly (not deferred, per this project's established practice of fixing real bugs hit during live testing):
- `jack_lsp`'s `-s`/`-S` server-name flag crashes on this machine's build ("buffer overflow detected", exit 134) - the `JACK_DEFAULT_SERVER` env var works fine and is used everywhere instead.
- `a2jmidid` does not honor `JACK_DEFAULT_SERVER` at all, only its own `-j` flag - using just the env var silently attached it to the host's real default JACK server instead of the isolated one. Caught via `jack_lsp -A` showing the bridged ports on the wrong server before any real interference happened; `native_adapter.py` always passes `-j` explicitly.
- Injecting `SCREEN_MIDI_RECORDER` crashed with `FileNotFoundError: .../zynthian-my-data/files/Midi` on both environments - that directory (plus its `patterns` subdir and `capture` symlink, present on every real hardware install via `zynthian-sys`'s `setup_system_raspioslite_64bit_trixie.sh`) was never scaffolded by this desktop port. Fixed in `docker/entrypoint.sh`'s scaffolding list and directly on the native `zynthian-my-data` tree.

`launch()` also had to learn to wait for actual boot completion, not just the OSC server coming up: `ZYNTHIAN-UI OSC server running` logs well before snapshot/engine/soundfont loading finishes on the same thread, so an early readiness check misattributed trailing boot noise (bank-load INFO lines, a harmless Bluetooth "Bad controller address" ERROR) to whatever step ran right after `launch()` returned. Fixed by waiting for the `SHOW SCREEN '<initial screen>'` line instead (see the log-level bug above for why that line needed fixing first) - it's reliably the last line of a normal boot.

### A "hung" Docker adapter that turned out to be a stale image

While validating `docker_adapter.py` (task 5), the first working launch appeared to hang indefinitely after `ZYNTHIAN-UI OSC server running` - identical symptom to the readiness-timing bug above, but this time waiting far longer (90s+) never produced `SHOW SCREEN` either. A screenshot of the container's actual X display (`import`/`identify`, same technique `test_zynthian_docker.sh` uses for its blank-screen check) proved the GUI had booted completely fine and was rendering the "Add Chain..." screen - not hung at all. `docker exec ... git log` on the running container showed it was built from a commit (`bfe70a9`) that predates this change's `SHOW SCREEN` log patch (`7a8a0e1`) entirely - the image was simply built (2026-09-24) before any of this change's fork commits existed, so the line `launch()` waits for could never appear. Rebuilding the image (`--build-arg CACHEBUST=...`) resolved it. Lesson for anyone hitting an apparent adapter "hang": check the running container's actual `zynthian-ui` commit (`docker exec <name> git -C /zynthian/zynthian-ui log --oneline -1`) before assuming the adapter or the app is broken - the Docker image only clones its own zynthian-ui/zynthian-webconf at *build* time (see `CLAUDE.md`), so it silently goes stale the moment a fork commit lands after the last build.

### `runner.py`'s two correctness bugs, found live building the shared core (task 3.3)

Building `workflow_testing/runner.py` (this decision's "shared step-execution core") ahead of group 7 surfaced two bugs in the assertion plumbing itself, both fixed:
- **Log buffering misattributed old lines to the wrong step.** Neither adapter set `PYTHONUNBUFFERED=1` on the launched `zynthian_main.py` process. Since its stdout/stderr aren't a TTY, Python block-buffers them - a line can be *generated* well before it's actually *flushed to the file*. This surfaced as the harmless boot-time Bluetooth "Bad controller address" line appearing to have been generated *during* a workflow step that ran seconds after boot actually finished, when it was really flushed late from earlier. Fixed by setting `PYTHONUNBUFFERED=1` in both adapters' launched-process environment.
- **`screen_is` assumed every correct outcome produces a fresh log line.** `show_screen()` only logs `SHOW SCREEN '<name>'` when the screen actually *changes* (`if self.current_screen != screen:` guard - see the screen-introspection decision above). A step targeting a screen that's already current (e.g. `SCREEN_MIXER` immediately after boot, which already defaults to mixer) is a legitimate no-op and produces no fresh line at all, so checking "did a new matching line appear this step" false-failed on a correct outcome. Fixed by tracking the last-known current screen across the whole workflow (seeded once from the log at session start, updated whenever a step's diff *does* contain a fresh line) instead of requiring one every step.

Separately (an app-behavior finding, not a bug in either of the above): injecting `SCREEN_CHAIN_MANAGER` as literally the first step against a freshly-booted session doesn't land there - it triggers the chain's FluidSynth engine to lazily start (several seconds of soundfont/bank/preset-loading log lines) and the screen ends up back on `mixer`, while also re-running the same "no Bluetooth controller configured" check boot already ran once (which is what surfaced the log-level bug fixed earlier in this file). The screen-landing behavior itself appears to be existing, real `zynthian-ui` behavior (no exception, no `build_view()` failure - `zynthian_gui_chain_manager.build_view()` always returns `True`), not something this change should paper over - workflows should simply avoid asserting `screen_is: chain_manager` as a session's very first step, or accept `mixer` as the settled outcome of a first "add an instrument" workflow (task 7.1) that starts from an engine-less default snapshot.

### Workflow-script format (task 1.2) - resolved

Plain data (YAML) over a Python DSL: a workflow is a list of steps, each either `{screen: SCREEN_NAME}` or `{zynswitch: <index>, press: short|bold|long}`, plus optional `assert:` blocks (`no_new_errors` implicit on every step; `screen_is: NAME` where the log patch above makes it cheap; workflow-level `save_snapshot`/`assert_zss`/`reload_and_check_audio`). Kept data-only (no code) specifically so a step list is trivially the same across both environment adapters - a Python DSL would risk environment-specific logic leaking into step definitions, which is exactly what the "one definition, both environments" requirement rules out.

### CUIA allow-list contents (task 1.3) - resolved

Enumerated from `zynconf/zynthian_config.py`'s `NoteCuiaDefault` against what the three starting workflows (task 7) need:
- `ZYNSWITCH 0` through `ZYNSWITCH 3` (notes 90-93) - the four base switches every workflow navigates with (back/up/down/select-equivalent on `TOUCH_ONLY` wiring).
- `SCREEN_CHAIN_MANAGER` (note 60), `SCREEN_MIXER` (note 64), `SCREEN_MIDI_RECORDER` (note 69) - direct jumps the three starting workflows use to reach their starting points.
- `ALL_NOTES_OFF` (note 12) - safe, used to clean up between workflow steps/note-injection tests without waiting for natural note decay.
Explicitly excluded (never added): `POWER` (0), `RESTART_UI` (4), `RELOAD_*` (5/7/9), `LAST_STATE_ACTION` (11), `SCREEN_ADMIN` (62) and anything only reachable through it. The list grows only when a new workflow script explicitly needs one more entry (design's existing "grow it deliberately" decision, now with a concrete starting set).
